    Course Description: DGX Evaluation for Textbook Generation¶

    Title: DGX Evaluation for Textbook Generation

    Target Audience: Professional development and adult continuing education. The course is written for AI and machine-learning engineers, instructional technologists, technical authors, and IT infrastructure leads who must decide whether a local NVIDIA DGX system can replace or supplement cloud AI services for generating interactive intelligent textbooks.

    Prerequisites:

    • Comfort with a Linux or macOS command line: navigating directories, editing files, running commands, and using SSH
    • Basic Python: reading a script, running it, and installing a package
    • Basic git and GitHub: clone, commit, push
    • Hands-on experience with at least one generative AI chat or coding assistant
    • No prior experience with GPU administration, model serving, or model training is required

    Course Overview¶

    Intelligent textbooks are usually generated by cloud-hosted frontier models driven by agent skills. This course asks an empirical question: can a single NVIDIA DGX system running an open-weight small language model (SLM) generate the same interactive intelligent textbook, end to end, without sending a token to the cloud? The course teaches how to answer that question with measurements instead of opinions. The benchmark workload is the ibook-skills skill chain, which turns a course description into a learning graph, chapters, MicroSims, a glossary, an FAQ, and quizzes.

    Students work through the full setup in the order a real evaluation requires. They reach the DGX over Tailscale, verify the hardware with Python probes, build a reproducible conda environment, choose and install an open-weight model and an inference server, and install an AI agent harness that executes skills against the local model. Each step ends with an explicit test, so a failure is caught where it happens and not three layers later. Students then run the textbook pipeline as a benchmark and score the results against a cloud-generated baseline of the same book.

    The course does not assume a specific DGX model. The DGX family spans x86_64 and aarch64 CPUs, single and multiple GPUs, and both dedicated GPU memory and unified memory, so the hardware probes run first and every later step branches on what they report. The same procedure applies to any DGX system a reader has access to.

    The course opens with a detailed case for and against SLMs. It compares local models with cloud services and agentic frameworks such as Anthropic Claude, OpenAI ChatGPT, Google Antigravity, and Devin, and it keeps three terms separate throughout: cost is what you pay to own and operate hardware, price is what a provider charges you for a service, and quality is how good the generated textbook is. The final deliverable is an evidence-based evaluation report that recommends a local, cloud, or hybrid workflow.

    An evaluation report is meant to be shared, and the raw material behind it is not safe to share. Probe reports, command output, logs, and screenshots carry addresses, hostnames, account names, and identifiers that make the tested machine easier to find and reach. The course therefore treats sanitization as a required step before anything is published.

    Software Stack Under Evaluation¶

    Layer Role in the evaluation Examples covered
    Remote access Reach the DGX from a laptop Tailscale, Tailscale SSH, MagicDNS
    Operating system Host OS, GPU driver, compute libraries DGX OS, NVIDIA driver, CUDA
    Environment Isolated, reproducible Python Miniforge, conda, pip
    Hardware probes Verify what the machine really has psutil, nvidia-smi, NVML Python bindings, PyTorch
    Model Open-weight SLM that does the generation Llama, Qwen, Gemma, Mistral, and Phi families
    Inference server Loads the model and exposes a local API Ollama, llama.cpp, vLLM
    Agent harness Runs the agent loop and executes skills Claude Code against a local endpoint, OpenCode, Codex CLI, Goose
    Skills The benchmark workload ibook-skills
    Site build Turns generated Markdown into the book MkDocs Material
    Sanitization Keeps device details out of published results Redaction script, placeholder conventions, a secret scanner such as gitleaks

    Main Topics Covered¶

    1. Intelligent textbooks and the generation pipeline. The five levels of intelligent textbooks, learning graphs, MicroSims, MkDocs Material, and the ordered ibook-skills skill chain used as the benchmark workload.
    2. Small language models. What separates an SLM from a frontier LLM: parameter count, context window, open weights, licenses, model families, model cards, and the capabilities textbook generation demands (long-form writing, structured output, tool calling, and code generation).
    3. Local SLMs versus cloud LLM services. Pros and cons of running a model on owned hardware compared with Claude, ChatGPT, Google Antigravity, and Devin: privacy, data sovereignty, rate limits, availability, vendor lock-in, version pinning, and operational burden.
    4. Cost, price, and quality tradeoffs. Capital cost, depreciation, electricity, and administration time; per-token, subscription, and per-seat pricing; total cost of ownership; cost per chapter; break-even volume; and quality-adjusted cost.
    5. NVIDIA DGX hardware architecture. The DGX product family treated model-agnostically: CPU architecture (x86_64 and aarch64), system RAM, GPU configuration, dedicated GPU memory versus unified memory, storage, power, thermals, DGX OS, the NVIDIA driver, and CUDA, and how each variation changes the setup steps that follow.
    6. Secure remote access with Tailscale. Mesh VPN concepts, WireGuard, tailnets, installing Tailscale on the laptop and the DGX, authentication, MagicDNS, Tailscale SSH, access control lists, key expiry, connectivity tests, and sharing a local web preview or model endpoint across the tailnet.
    7. Reproducible Python environments with conda. Miniforge, creating and activating environments, pinning the Python version, conda versus pip, environment.yml, requirements.txt, architecture-specific wheels, CUDA-enabled PyTorch, and rebuilding an environment from its specification.
    8. Python hardware probes. Scripts that report CPU model, core count, and architecture; system RAM; storage capacity and read speed; GPU count and model; driver and CUDA versions; total and free GPU memory; temperature; and power draw, all written to a machine-readable report.
    9. Model sizing and model fit. Parameters, numeric precision, bytes per weight, quantization levels, file formats (GGUF and safetensors), size on disk, context and KV-cache memory, safety headroom, and a calculator that predicts whether a model will fit before it is downloaded.
    10. Selecting and installing an open-weight model. Selection criteria, the Hugging Face Hub, license review, downloading, checksum verification, storage management, and shortlisting candidates.
    11. Inference servers. Installing and configuring a local runtime, GPU offload, OpenAI-compatible API endpoints, and a first-prompt smoke test from both curl and a Python client.
    12. AI agent harnesses and skills. The agent loop, tool calling, file editing, shell execution, permissions, context management, the Agent Skills SKILL.md format, connecting a harness to a local endpoint, installing ibook-skills, and verifying that a skill runs.
    13. Optimizing SLM performance. Quantization tradeoffs, context length, batch size, concurrency, prompt caching, sampling parameters, tokens per second, time to first token, GPU utilization monitoring, and thermal throttling.
    14. Objective evaluation methodology. Framing the question, controlled variables, cloud baselines, fixed inputs, repeated runs, metric selection, scoring rubrics, logging, sources of bias such as LLM-as-judge scoring, and blind human review.
    15. Running the textbook benchmark and reporting. An end-to-end generation run, per-stage metrics (skill completion rate, tool-call success rate, build success, structural validity, throughput, wall-clock time, energy, and cost per chapter), comparison with the baseline, and a written recommendation.
    16. Sanitizing evaluation artifacts before publication. The details that make a device easier to find, reach, or log in to: IP addresses, hostnames, tailnet names, usernames, passwords, keys, tokens, hardware identifiers, and access configuration. Redacting probe reports, command output, logs, and screenshots; placeholder conventions and documentation address ranges; scanning for secrets before a commit; and why a later commit does not remove data from git history.

    Topics Not Covered¶

    • Training and fine-tuning. The course evaluates inference only. Training a model from scratch, full fine-tuning, and LoRA adapters are out of scope.
    • Transformer internals. Deep-learning mathematics is limited to what is needed to estimate memory use and throughput.
    • Cluster-scale infrastructure. Multi-node clusters, Kubernetes, Slurm, and DGX SuperPOD deployments are not covered.
    • Non-NVIDIA accelerators. Apple Silicon, AMD, and Intel hardware appear only as brief comparison points.
    • Non-text generation. Image, audio, and video models for cover art or narration are not evaluated.
    • Retrieval systems. Retrieval-augmented generation, vector databases, and production chatbots are out of scope.
    • Enterprise security and compliance. Security coverage stops at Tailscale access control, basic host hygiene, and sanitizing published artifacts.
    • Textbook pedagogy. How to design a good textbook is covered by other books in this series. Here the pipeline is the workload, not the subject.
    • Cloud service tutorials. Cloud services appear as comparison baselines. The course does not teach how to use each one in depth.
    • Procurement. Purchasing negotiation and vendor selection are not covered beyond the inputs the cost model needs.

    Learning Outcomes¶

    After completing this course, students will be able to:

    Remember¶

    Retrieving, recognizing, and recalling relevant knowledge from long-term memory.

    • Define small language model, open-weight model, quantization, context window, token, inference, and agent harness.
    • List the DGX hardware components that determine inference capacity: CPU, system RAM, GPU, GPU memory, and storage.
    • Recall the stages of the ibook-skills textbook generation pipeline in order.
    • Name the Tailscale commands that join a tailnet, show device status, and test connectivity.
    • Identify the conda commands that create, activate, list, export, and remove an environment.
    • List common quantization levels and model file formats.
    • State the definitions of cost, price, and quality as used in this course.
    • Recognize the cloud services and agentic frameworks used as comparison baselines: Claude, ChatGPT, Google Antigravity, and Devin.
    • List the categories of device-identifying detail that must never appear in a published artifact.

    Understand¶

    Constructing meaning from instructional messages, including oral, written, and graphic communication.

    • Explain the reasons to prefer a local SLM over a cloud LLM service and the reasons not to.
    • Describe how parameter count and quantization determine a model's memory footprint.
    • Explain the difference between the cost of owning hardware and the price of a cloud service, and how each relates to output quality.
    • Describe how Tailscale builds an encrypted peer-to-peer mesh, and distinguish its coordination plane from its data plane.
    • Explain why an isolated conda environment makes an evaluation reproducible.
    • Summarize how an agent harness loads a skill, plans steps, and calls tools.
    • Explain the difference between dedicated GPU memory and unified memory and why it changes the model-fit calculation.
    • Interpret the output of nvidia-smi.
    • Explain why deleting sensitive data in a later commit does not remove it from git history or from an already published site.

    Apply¶

    Carrying out or using a procedure in a given situation.

    • Install and configure Tailscale on a laptop and a DGX, then connect over SSH using a MagicDNS name.
    • Create a conda environment with a pinned Python version, install the required libraries, and record the result in environment.yml.
    • Write and run Python probes that report CPU, system RAM, storage, GPU configuration, GPU memory, driver version, and CUDA version.
    • Calculate whether a model at a given quantization and context length fits in the available GPU memory.
    • Download an open-weight model, serve it from a local OpenAI-compatible endpoint, and send a first test prompt.
    • Install an agent harness, connect it to the local endpoint, install ibook-skills, and execute a skill.
    • Measure tokens per second, time to first token, GPU utilization, memory use, and power draw during a generation run.
    • Preview the generated textbook from a laptop across the tailnet.
    • Redact a probe report, a log excerpt, and a terminal screenshot using placeholders, then scan the result for secrets before committing it.

    Analyze¶

    Breaking material into constituent parts and determining how the parts relate to one another and to an overall structure or purpose.

    • Compare candidate open-weight models by license, size, context window, tool-calling reliability, and writing quality.
    • Diagnose a failed run by distinguishing out-of-memory errors, context overflow, malformed tool calls, and harness misconfiguration in the logs.
    • Break down the wall-clock time of a generation run into model loading, prompt processing, token generation, and tool execution.
    • Compare quantization levels by their effect on memory, speed, and output quality.
    • Differentiate the pipeline stages by their sensitivity to model capability: learning graph, chapter prose, MicroSim code, and quizzes.
    • Separate fixed costs from variable costs and identify the generation volume at which local hardware breaks even with cloud pricing.
    • Trace which data leaves the machine in each configuration, including inference traffic, Tailscale coordination metadata, and package downloads.

    Evaluate¶

    Making judgments based on criteria and standards through checking and critiquing.

    • Judge whether a given DGX configuration is sufficient for end-to-end textbook generation, citing probe and benchmark evidence.
    • Assess generated chapters, learning graphs, and MicroSims against a rubric and against a cloud-generated baseline.
    • Critique an evaluation design for bias, uncontrolled variables, too few repetitions, and unfair comparisons.
    • Justify a choice of model, quantization level, inference server, and agent harness using measured results.
    • Weigh cost, price, and quality to recommend a local, cloud, or hybrid workflow.
    • Assess the security of a remote-access setup built on Tailscale.
    • Review an evaluation report and its supporting files for leaked device details and judge whether it is safe to publish.

    Create¶

    Putting elements together to form a coherent or functional whole; reorganizing elements into a new pattern or structure.

    • Design a hardware probe suite that produces a machine-readable DGX configuration report with identifying fields redacted by default.
    • Build a model-fit calculator that takes parameter count, quantization, and context length and returns a fit verdict with headroom.
    • Construct an environment specification and install script that rebuilds the full software stack on a fresh DGX.
    • Develop a benchmark runner that executes the pipeline stages and logs metrics for each one.
    • Develop a cost model that compares the local cost per textbook with cloud pricing for the same book.
    • Compose an evaluation report that states the question, method, results, limitations, and recommendation.
    • Capstone project: Conduct a complete objective evaluation of a DGX system. Probe the hardware, select and install the software stack, generate a small intelligent textbook end to end with ibook-skills on the local GPU, compare it with a cloud-generated baseline of the same book, sanitize every artifact, and publish the report with a recommendation.
