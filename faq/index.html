    DGX Evaluation for Textbook Generation FAQ¶

    These are the questions readers ask most often. Each answer stands on its own and links to the chapter that covers the topic in full. Questions within each section run from the easiest to the hardest.

    Getting Started Questions¶

    What is this book about?¶

    It asks one empirical question: can a single NVIDIA DGX system running an open-weight small language model generate an intelligent textbook, end to end, without sending a token to the cloud?

    The book teaches you how to answer that question with measurements instead of opinions. You reach the DGX over a private network, verify the hardware with Python probes, build a reproducible environment, choose and install a model and an inference server, and connect an agent harness that runs the textbook-generation skills against the local model. Each step ends with a test, so a failure is caught where it happens and not three layers later. You then run the textbook pipeline as a benchmark and score the results.

    The final deliverable is an evidence-based evaluation report that recommends a local, cloud, or hybrid workflow. Throughout, the book keeps three terms separate: cost is what you pay to own and operate hardware, price is what a provider charges, and quality is how good the generated textbook is.

    Because the report is meant to be shared, and the raw material behind it is not safe to share, the book also teaches how to remove device details before anything is published. See the Course Description and Chapter 1.

    Who is this book for?¶

    The course is written for professional development and adult continuing education. The target readers are:

    • AI and machine-learning engineers,
    • instructional technologists,
    • technical authors, and
    • IT infrastructure leads

    who must decide whether a local NVIDIA DGX system can replace or supplement cloud AI services for generating interactive intelligent textbooks.

    It is not written for people who want to train or fine-tune models, build a cluster, or learn textbook pedagogy. Those are explicitly outside the scope (see the question on topics the course leaves out). It is a book about evaluating inference on one machine and deciding, with evidence, what that machine is good for.

    If you are making the decision for an organization and not running the benchmark yourself, the chapters on local versus cloud, cost, price and quality, scoring and bias, and diagnosis and reporting are the ones that matter most. See the Course Description and About.

    What do I need to know before I start?¶

    Four skills, each used in a specific later chapter:

    1. Command line. Navigate directories, edit files, run commands, and use SSH.
    2. Basic Python. Read a script, run it, and install a package.
    3. Basic Git and GitHub. Clone, commit, and push.
    4. Experience with a generative AI chat or coding assistant, enough to have a calibrated sense of how one fails. The typical failure is not nonsense, but an answer that is plausible, fluent, and slightly wrong.

    You do not need prior experience with GPU administration, model serving, or model training. The book builds those from the ground up.

    Chapter 1 reviews all four skills and ends each with a short worked example, so it works as a refresher and a self-test. If a command in it surprises you, spend an hour there before going on, because every later chapter asks you to type commands, read scripts, and commit files. A good habit from that chapter: before you run a command an assistant gives you, ask it to explain every flag, then run it in an empty scratch directory first. See the Course Description.

    Do I need my own DGX, and does the model matter?¶

    You need access to one for the hands-on chapters and the capstone, not necessarily to own it. The two units in this evaluation belong to someone else. The evaluator used an account the machine's administrator created, with no administrator rights, reached it through an invitation to the administrator's private network, and installed everything into a home directory. The Getting Started appendix records exactly what that took.

    The reading chapters need no machine at all: the case for and against local models, the hardware survey, and the cost model are written to be read. Chapters 7 and 8 prepare the connection and the tools, and Chapter 9 is where the step-by-step setup begins, with a test after every step.

    The DGX model does not matter, by design. The family spans x86_64 and aarch64 CPUs, single and multiple GPUs, and both dedicated GPU memory and unified memory, so the course runs the hardware probes first, and every later step branches on what they report. The worked example is a DGX Spark-class desktop unit with 128 GB of unified memory, and each time the book gives its measured value next to the general rule.

    If your machine differs, you will follow the same procedure and take a different branch. Run the probes in Chapter 10 and let the report tell you which. See Chapter 5.

    What will I be able to do when I finish?¶

    The course states its outcomes at all six levels of Bloom's Taxonomy. In practical terms, you will be able to:

    • Reach a DGX over Tailscale and SSH, with key-based login that scripts and agents can use.
    • Probe the hardware with Python and produce a machine-readable report with identifying fields left out.
    • Calculate whether a model fits in memory, with a safety margin, before you download it.
    • Serve an open-weight model from a local OpenAI-compatible endpoint and send it a first prompt.
    • Run an agent harness against that endpoint, install the ibook-skills chain, and execute a skill inside a container.
    • Measure tokens per second, time to first token, GPU utilization, memory, and power during a run.
    • Design a fair evaluation: one question, one varied factor, controlled variables, repeated runs, and a baseline.
    • Diagnose a failed run and compute cost per textbook.
    • Sanitize every artifact and publish a report with a recommendation.

    The capstone project ties it together: a complete objective evaluation of a DGX system that probes the hardware, generates a small intelligent textbook on the local GPU with ibook-skills, compares it with a cloud-generated baseline of the same book, sanitizes every artifact, and publishes the report. See the Course Description for the full list and Chapter 23 for the capstone steps.

    How is the book organized?¶

    The 23 chapters follow the order of a real DGX evaluation: understand the question, learn the hardware and the connection, build the software stack one verified layer at a time, run the benchmark, interpret the results, and sanitize everything before it is shared.

    Chapters Part What it covers
    1 to 4 The question and the vocabulary Intelligent textbooks, learning graphs, small language models, local versus cloud
    5 to 6 The machine and its cost DGX hardware, and the separate meanings of cost, price, and quality
    7 to 10 Reach and measure the machine SSH, Tailscale, conda environments, hardware probes
    11 to 15 Models and servers Sizing and fit, choosing a model, inference servers, candidates, performance
    16 to 18 The harness The agent loop, skills, containment and network boundaries
    19 to 23 Evaluate and publish Fair design, scoring and bias, running the benchmark, diagnosis and reporting, sanitizing

    Each chapter lists the earlier chapters it builds on, and no concept appears before its prerequisites, because the order is derived from the book's learning graph. After the chapters come the appendices, which hold the record of the evaluation itself, and the Model Results, which hold what each model produced. See the chapter list.

    What exactly does the benchmark ask a model to generate?¶

    The input is the description of a high school Algebra I course, the same unchanged copy every time. The model must produce three things, in order, by running three skills:

    1. A learning graph of 200 concepts and their dependencies, as a CSV and a JSON file that agree.
    2. A book structure that places every concept into a chapter, with no chapter needing a concept the book has not yet taught.
    3. Chapter content for each chapter, run once per chapter. A chapter counts as written when its placeholder is gone and it has at least 1,000 words.

    Each stage has a time limit: 150 minutes for the learning graph, 2 hours for the book structure, and 90 minutes for each chapter.

    The scope is deliberately narrow. The benchmark does not generate MicroSims, a glossary, an FAQ, or quizzes. Algebra I was chosen because a published book already exists to serve as a reference for scale (200 concepts, 13 chapters, and about 55,000 words of chapter text), and because it is familiar enough that a reviewer can judge the output without special expertise.

    The reference book is not a baseline. It was made with earlier skill versions and no timings were kept. See Chapter 21 and Chapter 1.

    What does the book leave out on purpose?¶

    The course description lists ten exclusions, so that nobody expects them:

    • Training and fine-tuning. The course evaluates inference only. Training a model from scratch, full fine-tuning, and LoRA adapters are out of scope.
    • Transformer internals. The mathematics is limited to what is needed to estimate memory use and throughput.
    • Cluster-scale infrastructure. Multi-node clusters, Kubernetes, Slurm, and DGX SuperPOD deployments.
    • Non-NVIDIA accelerators. Apple Silicon, AMD, and Intel appear only as brief comparison points.
    • Non-text generation. Image, audio, and video models.
    • Retrieval systems. Retrieval-augmented generation, vector databases, and production chatbots.
    • Enterprise security and compliance. Security stops at Tailscale access control, basic host hygiene, and sanitizing published artifacts.
    • Textbook pedagogy. How to design a good textbook is covered by other books in this series.
    • Cloud service tutorials. Cloud services appear as comparison baselines, not as subjects.
    • Procurement. Purchasing negotiation and vendor selection, beyond the inputs the cost model needs.

    An explicit exclusion costs one line and prevents a chapter nobody wanted. That is also a lesson the book teaches about course descriptions: a model asked to write about a DGX will happily write about training and fine-tuning unless the description rules it out. See the Course Description.

    How should I read the book, and what are the quizzes and references for?¶

    Read the chapters in order, because concepts are introduced in dependency order and no concept appears before its prerequisites. Each chapter has three pages:

    • Content, the chapter itself, which ends in a short summary.
    • Quiz, ten multiple-choice questions spread across the Bloom's Taxonomy levels. Each answer is hidden behind a "Show Answer" control that explains why the correct option is correct, names the concept tested, and links back to the chapter section to review.
    • Annotated References, ten curated sources, each with a note on why it is relevant to the chapter.

    Use the other tools as they come up:

    • MicroSims. Try each interactive simulation as you meet it. They are the fastest way to build intuition for a new concept, and each embeds a fullscreen link.
    • The search bar at the top right, to jump to a specific term, and the Glossary, which defines every concept in the learning graph in one precise sentence with an example.
    • The learning graph viewer, to see how a concept fits the whole book. Search for a concept and click it to see its prerequisites and dependents.

    Do each step's test before moving to the next. The hands-on chapters end every step with a test so that a failure shows up at the step that caused it. See About and the Learning Graph.

    Who is Tera?¶

    Tera is the book's learning mascot: a compact silver-white robot with a tool belt that holds a stopwatch, a digital caliper, and a tape measure, which are the benchmarking tools. Tera is precise, practical, and evidence-minded, and has no gender, so the book writes "Tera" or "they".

    Tera's catchphrase is "Measure first, then decide!", and it is also the book's method. A claim about a model counts only when it comes with a number you can check.

    Tera appears in chapters in six roles, and each is a signal and not decoration:

    1. Welcome opens a chapter and says what you will be able to do by the end.
    2. Think flags a mental model worth slowing down for.
    3. Tip hands you a shortcut you can use immediately.
    4. Warn marks a known trap and shows you how to avoid it.
    5. Encourage appears where the material is notoriously hard.
    6. Celebrate closes a chapter by naming what you just accomplished.

    If Tera is not doing one of those six things, Tera is not in the chapter. The warnings are a good place to start when you are short of time, because each one states a pitfall, why it happens, and exactly how to avoid it. See Chapter 1.

    Why does the book use placeholders instead of real addresses and names?¶

    Because the site and its repository are public, and the machine being evaluated is real. A login, address, hostname, or token published once is exposed for good, so the book contains none. Every example uses a placeholder that is impossible to mistake for a real value:

    ssh <user>@<dgx-host>

    Replace each placeholder with the value your own administrator gives you, and never copy your real values into a file you plan to publish. The conventions are:

    Core Concept Questions¶

    What is an intelligent textbook?¶

    An intelligent textbook is a textbook whose content is structured so that software can read it, check it, and respond to the reader. Two properties define it. The first is explicit structure: the concepts, their dependencies, and the learning outcomes are stored as data, not only implied by the prose. The second is interactivity: the book contains elements the reader operates, such as MicroSims and quizzes, that report back what the reader did.

    A static textbook might explain quantization with a paragraph and a table of numbers. An intelligent textbook gives the same concept a place in a dependency graph, so the book knows which concepts must come first. It also adds an interactive simulation where the reader moves a precision control and watches the memory estimate change, and a short quiz that records which options the reader chose.

    This is also why textbook generation can be benchmarked at all. An intelligent textbook is a set of plain Markdown files plus a build, so a model can write it and a program can check it. Chapter 1 gives the full definition, and Chapter 2 explains the structure underneath.

    What are the five levels of intelligent textbooks?¶

    The levels are a five-step scale for how much intelligence a book has. Each level adds a capability the previous one lacks:

    1. Static content. Fixed text and images, with no navigation aids or interactivity.
    2. Interactive content. Hyperlinks, quizzes, MicroSims, and a searchable glossary.
    3. Adaptive content. Material that changes with the reader's demonstrated progress.
    4. Chatbot integration. A conversational tutor that answers the reader's questions in real time.
    5. Autonomous AI. Fully customized lessons generated in real time for each reader.

    The higher levels are progressively more aspirational. This book targets Level 2 and above, so it contains MicroSims and quizzes. The books the full ibook-skills chain generates are Level 2 books: Markdown prose, interactive elements, quizzes, and a glossary. The benchmark runs only the first stages of that chain. A conversational tutor or per-reader lessons belong to Levels 4 and 5, and they are not what makes a textbook "intelligent" in the sense this book uses. See Chapter 1 for the table and the Book Levels MicroSim.

    What is a MicroSim?¶

    A MicroSim is a small, self-contained interactive simulation, embedded in a textbook page, that demonstrates exactly one idea. The scope is the point: a MicroSim has one learning objective, a few controls, and a result the reader can see change. A slider that redraws a chart as the reader changes a value is the typical shape.

    Each MicroSim lives in its own folder under docs/sims/, named by a short lowercase identifier. The folder holds a main.html that runs the simulation and an index.md lesson page that describes it. A chapter embeds the simulation with an iframe that points at main.html, so the same simulation can also be opened fullscreen or reused in another book.

    Two examples in this book are the Parameters That Fit in Memory MicroSim, where you move a memory slider and see the largest model whose weights fit, and the Testing Architecture MicroSim, which steps through how the evaluation machines connect. Most MicroSims are p5.js programs, and the book requires p5.js's own built-in controls such as createSlider and createButton. See Chapter 1 and Chapter 2.

    What is a small language model?¶

    A small language model (SLM) is a language model small enough to run on a single machine you control. There is no universal parameter threshold, and the boundary moves as hardware improves. This book uses a working definition tied to the machine under test: a model that fits in the memory of one DGX system and can be served from it.

    The definition has two parts, and a model can pass one and fail the other. In this evaluation's first round, qwen3.8:27b downloaded as 17 GB and completed the first benchmark stage, so it is usable as an SLM on one DGX unit with 128 GB of memory. mistral-medium-3.5:128b is an 80 GB download that loaded and ran at 3 tokens per second, but no context of 64,000 tokens or more fit. You can own that model, yet on this machine it is not a small one in the sense that matters. The answer for the same model could change on a larger system.

    A frontier model, by contrast, is one of the most capable models available at a given time, typically run by a leading AI lab as a cloud service, with weights that are usually not released. See Chapter 3.

    What abilities does textbook generation demand of a model?¶

    The benchmark exercises five abilities:

    1. Instruction following. Doing what a prompt or a document of instructions says, including its constraints, in the order given. A skill file that runs past a thousand lines is a long instruction, and a model that drifts from it breaks the rules it was handed.
    2. Long-form writing. Sustained, coherent prose across many paragraphs, with consistent terminology and a stable argument. It tests whether a model stays on topic and avoids repeating itself.
    3. Structured output. Output that conforms to a required format, such as a JSON object with named fields of given types. One missing field or stray character can break a whole step.
    4. Tool calling. Asking a program to act on the model's behalf by emitting a structured request, then using the result.
    5. Code generation. Writing shell and Python scripts the agent uses to do its work, and the JavaScript for MicroSims. Code can be run, so it can be checked.

    Two more concepts appear in model descriptions but are not scored: reasoning mode, which spends extra tokens working through a problem, and multimodal input such as images, which the benchmark does not use. See Chapter 3.

    What are Tailscale and a tailnet?¶

    Tailscale is a service and a set of client programs that build a WireGuard mesh VPN automatically. By hand, WireGuard asks you to generate a key pair on each device, copy each public key to every peer, find each peer's current public address, and write a config file per device. Tailscale does all of that: the client generates its keys at first start, a coordination service distributes public keys and tracks addresses, and the clients negotiate a path across the routers with a relay as the fallback. The client software is open source, and the coordination service is hosted.

    A tailnet is the private network of devices and users managed together under one Tailscale account or organization. Members get stable private addresses from a reserved range that starts with 100., and they get names that resolve only inside the tailnet. The tailnet's administrator controls who is a member and what each may reach.

    In this evaluation the laptop signed in with an account the administrator had invited, the DGX units were already members, and one status command listed all three. A tailnet has a name in the form <tailnet-name>.ts.net, which this book always writes as a placeholder, because like an address it helps a stranger locate the network. See Chapter 7 and Chapter 9.

    What is a conda environment, and why does the evaluation use one?¶

    A Python environment is a self-contained directory that holds a Python interpreter and the packages installed for it, plus a script that points your shell at them. Activating it puts its interpreter and packages first on your path, so python runs that interpreter and import finds those packages and no others. Conda is the tool that creates, activates, exports, and removes them, and it also installs non-Python programs and Python itself. This book installs it with Miniforge, a minimal installer that uses the community conda-forge channel by default, because a commercial default channel can carry license terms a book for professionals in unknown organizations should not depend on.

    The need is clearest without one. If two projects share one system Python and need different versions of a library, installing for the second silently breaks the first, and the failure may not appear until a script that worked last month errors out. This course had a real case: two documentation build tools each pinned a different version of the same markdown-extension package. The fix was not a cleverer install. It was a separate environment for each tool.

    The conda create command makes one, as in conda create -n dgx -c conda-forge python=3.12: -n names it, -c names the channel, and a version after an equals sign pins a package. That is environment isolation, and it makes the evaluation reproducible: a surprising result can be traced to a cause instead of to "something I installed last week". The book uses a dedicated tool environment named dgx that holds only the Tailscale client and daemon. Treat an environment as a directory you can throw away. You never repair a broken one; you delete it and rebuild it from its specification. See Chapter 8.

    What is the ibook-skills chain, and which steps does the benchmark run?¶

    The ibook-skills chain is the ordered set of skills that builds an intelligent textbook. Each skill takes the previous one's output as its input, so the order is part of the design:

    Step Skill What it produces
    1 course-description-analyzer A validated course description, scored for completeness
    2 learning-graph-generator The concept list and dependency graph
    3 book-chapter-generator The chapter structure, one outline per chapter
    4 chapter-content-generator The text of each chapter
    5 microsim-generator The interactive simulations
    6 glossary-generator Definitions of the concepts
    7 faq-generator Frequently asked questions
    8 quiz-generator Chapter quizzes
    9 reference-generator Citations for each chapter
    10 book-installer Site features such as the mascot and graph viewer

    The benchmark runs three of the ten, steps 2 through 4, and uses step 1 as a short check that the wiring works. MicroSims, the glossary, the FAQ, and the quizzes are outside it.

    Each stage is started by a fixed prompt. The first stage's prompt names the skill, points at the course description, asks for 200 concepts, and ends with a standing approval answer: because nobody is present, any time the skill asks a question or waits for review, treat it as approved and continue, work through every step, and stop when the skill is complete. Without that answer, a skill that stops to ask "does this look right?" would wait forever. See Chapter 17.

    What must never appear in a published artifact?¶

    Device-identifying details are the facts that help a stranger find, reach, or log in to a specific machine. This book's repository and site are public, so the rule is fixed and applies to every contributor, human or automated:

    Category Examples Why it matters
    Network addresses Tailnet addresses, public addresses, IPv6 addresses Tells a scanner where to look
    Names Hostnames, MagicDNS names, the tailnet's name Locates the machine and the network
    Accounts Usernames, passwords, passphrases The login itself, or half of it
    Keys and tokens SSH keys, Tailscale auth keys, model-hub tokens Access without a password
    Hardware identifiers Serial numbers, GPU unique identifiers, MAC addresses Identifies the physical unit
    Access configuration The access control policy, open ports, firewall rules Shows exactly how to get in
    Raw logs Unedited command output and run logs Contains any of the above, unpredictably

    Two points are easy to miss. A tailnet address starting 100. only works inside the tailnet, and it is still an identifier, because it names a specific device in a specific network. And access configuration is the most useful single document to someone planning an attack, because it lists what is allowed, so it is never published, in whole or in part, for a real device.

    Sanitization is the step that removes or replaces these details, with its own checks. It is a step in the pipeline, not a final polish. See Chapter 23.

    What is a learning graph and why does the book start from one?¶

    A learning graph is a directed acyclic graph of a course's concepts in which each edge is a concept dependency: a statement that one concept must be understood before another. In practice it is two lists stored together, the concepts (each with an identifier, label, and category) and the dependency edges between them. This book stores the graph as both a CSV file and a JSON file, and the two must agree.

    This book fixes one convention: an edge points from the dependent concept to its prerequisite. The edge Percent → Decimals reads "Percent needs Decimals". This book's own graph has 506 concepts, 824 edges, 12 foundational concepts with no prerequisites, and a longest dependency chain of 16 concepts.

    The graph does not store a chapter order. It stores what depends on what, and any order that respects those dependencies is valid, which is why the same graph can be regrouped into a different number of chapters. Everything downstream is derived from it: the chapters partition its concepts, the glossary is generated from its concept list, and each quiz question traces back to one of its nodes. A flaw in the graph therefore spreads everywhere. See Chapter 2.

    Why must a learning graph have no cycles?¶

    A cycle is a path that starts at a concept and, by following dependencies, returns to it. A learning graph must be a directed acyclic graph because a cycle makes a teaching order impossible: if A needs B, B needs C, and C needs A, there is no concept you can learn first.

    A valid graph always has at least one topological order, in which every concept comes after all of its prerequisites. To find one, repeatedly take a concept whose prerequisites have all been taken. Consider three dependencies: Percent needs Decimals, Decimals needs Fractions, and Ratios needs Fractions. Fractions needs nothing, so it goes first. Then Decimals and Ratios are both available, and Percent follows Decimals. Fractions, Decimals, Ratios, Percent is one valid order, and Fractions, Ratios, Decimals, Percent is another. Having more than one valid order is normal.

    Now add the line "Fractions needs Percent". Fractions can no longer come first, because it needs Percent, which needs Decimals, which needs Fractions. No valid order exists. This is why the benchmark's structural checks include a dependency cycle check on every generated graph. See Chapter 2 and Chapter 20.

    What is a Concept Impact Score?¶

    The Concept Impact Score (CIS) measures how much of a learning graph rests on a concept. It is defined recursively: a concept's score is 1, counting itself, plus the scores of every concept that depends on it directly.

    Work from the end of a small graph to see it. Suppose B needs A, C needs A, D needs B, D needs C, E needs D, and F needs C. E and F have no dependents, so each scores 1. D has one dependent, E, so D scores 1 + 1 = 2. C has dependents D and F, so C scores 1 + 2 + 1 = 4. B has dependent D, so B scores 1 + 2 = 3. A has dependents B and C, so A scores 1 + 3 + 4 = 8, the highest, because it is the most foundational.

    The score accumulates through chains, so a concept deep in the foundations can score very high even when only one or two concepts depend on it directly. In this book, Generative AI Assistant Use scores 2,518 and Generative AI Model scores 2,364, while 193 of the 506 concepts score exactly 1. Most of the book is narrow detail resting on a small foundation. The CIS also decides how many words each concept gets; see Chapter 2.

    What is the difference between an open-weight model and an open-source model?¶

    An open-weight model is one whose trained parameters are published for anyone to download and run. That lets you run it locally and inspect or fine-tune it. It does not necessarily mean the training data, the training code, or the right to do anything you like with the weights are also public.

    Closed model Open-weight model Open-source model
    Weights downloadable No Yes Yes
    Training data and code published No Usually not Yes
    Runs on your hardware No Yes Yes
    Use is governed by Provider terms of service A model license An open-source license

    The distinction matters because a model's weights can be public while its training data, its training code, and the right to do anything you like with it are not. Each model ships with a model license that may be a standard permissive license such as Apache 2.0 or MIT, or a custom one that restricts use. One candidate in this evaluation is released under a modified MIT license that allows commercial use but carves out an exception for companies with large revenue, and another's page does not state a license at all. Always read and record the license before you build a workflow on a model. See Chapter 3 and Chapter 12.

    What is a context window, and how do I check that a document fits?¶

    The context window is the maximum number of tokens a model can consider at one time, counting both the text it is given and the text it generates. When a conversation grows past the window, something is dropped or the request fails. The limit is measured in tokens, not words, and in a multi-turn session it is a running total: each turn adds the earlier conversation, every file the model has read, and every tool result.

    To check a document, convert words to tokens, add room for the reply, and compare with the window. A common planning figure is about 1.33 tokens per word of ordinary English, which understates text full of code, numbers, or technical terms. Suppose a model has an 8,000-token window, and you want to summarize a 5,000-word document with a reply of up to 2,000 tokens. The document is about 5,000 × 1.33 = 6,650 tokens. With the reply, you need about 8,650 tokens, which is more than 8,000. The document fits by itself, and the task does not. For a real decision, run the text through the model's own tokenizer, because each model has its own vocabulary and its own count.

    The window is a property of the model. The context length a server is configured to use is a separate setting, and it is the one that reserves memory. A longer context takes memory from the same pool as the model's weights, so the largest advertised window is often not the largest usable one. See Chapter 3 for the arithmetic and Chapter 11 for the memory cost.

    What is tool calling, and does the model run commands itself?¶

    No. A language model never touches your machine. It only produces text, and one kind of text is a structured request that a separate program, the harness, chooses to carry out. The harness runs the command and returns the result to the model as new text.

    One round of the exchange looks like this:

    Step Who What happens
    1 User Asks "How many lines are in notes.txt?"
    2 Model Emits a tool call: {"name": "run_shell", "arguments": {"command": "wc -l notes.txt"}}
    3 Harness Runs wc -l notes.txt and returns 3 notes.txt
    4 Model Reads the result and answers "It has 3 lines."

    Tool calling depends directly on structured output, because step 2 must be valid JSON for the harness to execute it. That explains two failure types you will meet later: a malformed tool call, which has a wrong name, a missing argument, or an argument of the wrong type, and a text-emitted tool call, where the model writes the request as ordinary prose, so the harness sees nothing to run and no work happens. See Chapter 3, Chapter 16, and Chapter 22.

    How does a language model produce text?¶

    A large language model is trained on very large amounts of text to predict what comes next. Given the text so far, it assigns a probability to every possible next piece of text, one piece is chosen and appended, and the step repeats until a stop condition is met. For the input "The capital of France is", an illustrative step might give " Paris" a probability of 0.92 and divide the remaining 0.08 among all the other candidates.

    Two consequences matter for this book. First, a model writes one token at a time and each token depends on everything before it, so a mistake early in the output is never revisited, only built upon. That explains both its fluency and its failures. Second, everything the model knows was fixed when training ended. During use it sees only the text it is given, so it cannot read your files or run your commands unless a harness puts that text in front of it.

    Running a trained model to produce output is inference, as distinct from training, which created its parameters. This course evaluates inference only. See Chapter 3.

    Why would I run a model locally instead of using a cloud service?¶

    A local model deployment gives you control: you choose the model, the version, and where every token goes. The reasons usually come down to four properties:

    • Privacy. Your prompts and attached files stay on your network, and no provider records usage metadata about them.
    • Data sovereignty. You know which jurisdiction processes the data, because it never leaves your site. For regulated or contractual data this can decide the question before cost enters.
    • Offline operation. Once the model and tools are installed, a local deployment runs with no network connection. The setup itself still needs a network to download them.
    • Version pinning. Keep the weights file and record its name and checksum, and the model cannot change unless you change it.

    The price of that control is operational burden: installing and updating the driver and server, watching memory and temperature, handling failures, and managing storage. It is staff time, and it is a cost even when no money changes hands. You are also limited to models that are open-weight and fit your hardware. In this evaluation a unit froze during long runs, and a memory watchdog now runs before any model does. See Chapter 4.

    What are the drawbacks of relying on a cloud LLM service?¶

    Four drawbacks are really one fact seen from four sides: the model lives on someone else's schedule.

    • Rate limits cap how many requests or tokens you may use in a period. A job that must generate dozens of chapters in sequence can stall or be slowed to the provider's pace, however much you are willing to pay.
    • Service availability is outside your control. A cloud service has outages and degraded periods you cannot fix and often cannot predict. A local deployment has outages too, but you can see and repair them.
    • Model deprecation retires a model version, after which requests fail or are redirected to a newer one. A benchmark result recorded against a deprecated model can no longer be reproduced.
    • Vendor lock-in is the cost of switching once your prompts, tooling, and habits are tuned to one provider's behavior.

    None of these is a reason to avoid a cloud service. The convenience is real: no hardware, no installation, no model management, and access to the strongest models, which are often not released any other way. The point is to know which of the four your workflow can tolerate. See Chapter 4.

    What is a hybrid workflow?¶

    A hybrid workflow uses a local model for some steps and a cloud service for others. The split can follow one of three things:

    • Data sensitivity. Confidential content stays local, and non-sensitive drafting goes to the cloud.
    • Stage. A cheap local model produces first drafts, and a frontier model polishes the result.
    • Volume. Steady high-volume work runs locally, and rare peak demand overflows to the cloud.

    A hybrid is routing, not compromise. Each step goes where its own requirements are best met, which means you have to know each step's sensitivity, volume, and quality demands. That is why the question "local or cloud?" usually has no single answer for a whole project. Break the work into steps first, and the answer often becomes obvious, and often differs from step to step.

    For textbook generation, the pipeline itself suggests a split by stage. An illustrative reading of this evaluation's first round, which is provisional because every result is one run, is that several models completed the learning-graph and chapter-structure stages while the chapter text exposed the capability differences. That pattern would point to local structural stages and a stronger model for the hard prose, until a local model's prose is reviewed. The benchmark reports per-stage results precisely so that you can make that kind of split with evidence. See Chapter 4 and Chapter 22.

    What is an agentic framework, and how is it different from a model?¶

    An agentic framework is software that wraps a language model with tools, memory, and a planning loop so it can carry out multi-step tasks such as reading files, running commands, and revising its own work. The model supplies the language ability, and the framework supplies the structure that lets it act. Tool calling is the mechanism, and Chapter 16 builds the loop.

    Frameworks matter for a local-versus-cloud comparison because many are tied to one provider's models and sold with them. When you run a task through such a framework, the quality you observe is the quality of the model and the framework together. Two well-known examples are Google Antigravity, an agent-oriented development environment where AI agents plan and carry out coding tasks, and Devin, an AI software-engineering agent from Cognition that takes a task, works through it in its own environment, and returns code. With either, you buy the outcome of a whole loop and generally do not choose the underlying model.

    This evaluation uses a framework in a different way. The harness is Claude Code, but it is pointed at a local endpoint, so the loop is Anthropic's tooling while every token comes from the local model. See Chapter 4 and Chapter 17.

    What is the difference between dedicated GPU memory and unified memory?¶

    Dedicated GPU memory belongs to the GPU alone, mounted on its own board and connected by a very fast link. A model loaded onto such a GPU must fit entirely in that memory. A DGX H100 holds eight H100 GPUs with 80 GB each, 640 GB in total, and each 80 GB pool is a hard limit: a model whose weights take 100 GB cannot sit on one GPU, however much system RAM the server has, and must be split across at least two.

    Unified memory is a single pool shared by the CPU and the GPU, so both read and write the same physical chips. The GB10 in a DGX Spark uses it, and its 128 GB is the whole machine's memory, with nothing set aside for the GPU.

    The consequences run both ways:

    • A larger model can fit, because the limit is the whole pool. A 65 GB model that would not fit a 24 GB gaming GPU loads on this machine.
    • Everything competes. Weights, context, the operating system, and every other program draw on the same 128 GB, so a model that fits on paper can still starve the system.
    • Exhaustion can freeze the machine, because the pool is also what the operating system runs on.

    Every fit calculation changes accordingly. See Chapter 5 and Chapter 11.

    What is the difference between cost, price, and quality?¶

    The three terms answer different questions, and a sentence that blurs them cannot be answered:

    • Cost is what you pay to own and operate something: the hardware share, setup labor, electricity, and administration that a result uses up. It belongs to whoever bears it.
    • Price is what a provider charges you for a service. It covers the provider's costs and a profit, and it can move for reasons unrelated to cost, such as competition.
    • Quality is how good the output is. It is neither a cost nor a price, and it is the term most often left out of a comparison.

    A worked example: a cost of $53 per book on your own machine and a price of $20 per book from a service are not comparable unless the service produces the same book to the same standard. And a local model that costs half as much but writes a learning graph with 40 duplicate labels has not saved half. It has produced something that must be redone or reviewed at further cost.

    When someone says something is cheap, expensive, or good, ask which of the three they mean. Most comparisons that look contradictory are two people answering different questions. See Chapter 6 and the Cost Analysis appendix.

    What does it cost to own and run a DGX for textbook generation?¶

    The book's reference case for one DGX Spark-class unit used for textbook generation comes to about $8,275 a year:

    Part Calculation Per year
    Hardware ($6,950 + $250) spread over 3 years $2,400
    Setup labor 40 hours × $90, spread over 3 years $1,200
    Electricity 832 kWh × $0.1385 $115
    Operations labor 4 hours a month × 12 months × $90 $4,320
    Network and space $20 × 12 months $240
    Total $8,275

    Two things stand out. People's time is about two thirds of the total, and electricity is about one percent. And every row is an assumption except the hardware's list price, so the total is a model's output, not a measurement. Over the assumed three-year life, the total cost of ownership is about $24,825, which includes the $7,200 purchase and $3,600 of setup labor at full size.

    The hardware row is the capital cost, $7,200 for the unit and accessories, spread evenly by depreciation over an assumed three-year lifespan with no resale value. That lifespan moves the answer: stretch it to five years and the cost per book falls from $53 to $44. See Chapter 6 and the Cost Analysis appendix for every assumption.

    Why are fixed and variable costs the key difference between local and cloud?¶

    The two options have opposite cost structures, and that gives them different risks.

    For local generation, fixed costs are nearly the whole bill: about $8,160 of the $8,275 a year in the reference case. Depreciation, setup labor, and monthly operations labor are the same in a year with 10 books and a year with 150. The one variable cost is the electricity used while generating, which is about $0.58 per book. A cloud service is the mirror image: its price is almost entirely variable, because you pay per token or per seat and nothing when you do not use it.

    Local generation Per-token cloud service
    Fixed cost per year High, about $8,275 None
    Variable cost per book Very low, about $0.58 The price per book
    Cost if you make no books Still $8,275 $0
    Cost per book as volume rises Falls Stays constant

    The consequence is that the cost of one more local book is close to zero, while the cost of owning the machine is large and unavoidable. A local machine rewards steady, high volume and punishes idleness. A cloud service rewards occasional use. See Chapter 6.

    Why use a mesh VPN instead of port forwarding or a conventional VPN?¶

    Judge each approach against the constraints of the real situation. In this evaluation the laptop and the DGX are on different home networks, nobody involved controls both routers, the person running the benchmark has no access to the DGX's router, scripts and an agent must log in with no person present, and the machine must not be reachable by strangers.

    Constraint Port forwarding Conventional VPN Mesh VPN
    No access to the DGX's router Fails: needs a router change Works if the server is reachable Works
    Scripts must connect unattended Works Works Works
    Must not be reachable by strangers Fails: the login port is public Works Works
    No new server to run and patch Works Fails: someone runs the hub Works

    Only the mesh VPN passes every row. Port forwarding is the approach a tutorial reaches for first, and this course does not use it: a login service open to the whole internet receives guessing attempts within minutes, and exposing a DGX that way endangers the machine and the network it sits on.

    The underlying reason is NAT. A home router drops any connection nobody inside asked for, so two machines behind two routers cannot simply connect. A mesh VPN solves that problem without opening a door on the machine. See Chapter 7.

    What is a hardware probe, and why not just read the spec sheet?¶

    A hardware probe is a small, read-only measurement of one fact about a machine: how many cores it has, how much memory is free, which GPU is installed. A specification sheet tells you what a machine was built to be. A probe tells you what it is right now, after a driver update, a reboot, or a move to a different DGX.

    Each probe has three parts: the question, the source it reads, and the form of the answer.

    Probe Question it answers Source it reads
    CPU probe Which architecture, and how many cores? platform, os, lscpu
    RAM probe How much memory is total, and how much is available? /proc/meminfo
    Storage probe How big is the disk, and how much is free? shutil.disk_usage
    GPU probe Which GPU, driver, temperature, and power? nvidia-smi
    CUDA version probe Which CUDA version does the driver support? The nvidia-smi header
    Unified memory probe Does the GPU have its own memory? The GPU memory field

    The GPU probe asks nvidia-smi for exactly the fields it wants, with --query-gpu and --format=csv,noheader,nounits, because the table meant for people changes layout between versions. A probe script runs one or more probes and prints the results, and a probe suite combines them into one JSON report that later steps consume. A model-fit calculator reads the report's available_gib, and a benchmark runner records the whole report beside each result so that a number is never separated from the machine that produced it. See Chapter 10.

    What is quantization, and what does "4-bit" really mean?¶

    Numeric precision is how many bits are used to store each number, and quantization stores a model's weights with fewer bits than the original, trading a small loss of accuracy for a large saving in memory and a gain in speed. A quantization level names how aggressively. Memory for weights is parameters times bytes per weight, so the same 27-billion-parameter model is a very different problem at each precision:

    Precision Bytes per weight Memory for weights
    16-bit 2 54 GB
    8-bit 1 27 GB
    4-bit 0.5 13.5 GB

    8-bit keeps nearly all of the original's quality at half the 16-bit size. 4-bit cuts it to a quarter, with a loss that is small for most tasks and larger for hard reasoning. File names carry the level in a code such as Q4_K_M or Q8_0, and a model library's default tag is usually 4-bit.

    A "4-bit" file is not exactly 4 bits per parameter. It stores scaling factors and keeps some sensitive layers at higher precision. Four "4-bit" files in this evaluation measured between 4.4 and 5.7 effective bits per parameter, so a planner who used 4.0 underestimated the weights by 10 to 30 percent. Use the download size when you have it, and about 5 bits when you only have a parameter count. How much quantization hurts quality is an evaluation question, not a calculation; Chapter 15 returns to it. See Chapter 11.

    What is the KV cache, and why does the context setting change memory use?¶

    The KV cache is the memory a model uses to remember the conversation so far. For every token in the context, the model keeps a key vector and a value vector at every layer so it does not recompute them for each new token. The cache grows by a fixed amount per token:

    KV bytes per token = 2 × layers × KV heads × head dimension × bytes per value

    With an illustrative shape of 48 layers, 8 key-value heads, a head dimension of 128, and 2 bytes per value, that is 192 KiB per token. The context length memory is that amount multiplied by the context length you allow:

    Context length KV cache
    32,768 tokens 6.4 GB
    131,072 tokens 25.8 GB
    262,144 tokens 51.5 GB

    The cache is allocated for the context length the server is configured with. You cannot ignore it until the conversation gets long. This evaluation measured a 20 GB model sitting idle: one unit showed 29 GB in use at a 32,000-token setting and 66 to 71 GB at a 256,000-token setting, a difference of about twice the model's size.

    A context setting is therefore a memory reservation, made on the same pool the operating system lives in. Choose the smallest context the job needs, and raise it deliberately while watching available memory. See Chapter 11.

    Does a mixture-of-experts model need less memory than a dense model?¶

    No. It needs just as much memory for its size, and it saves time per token instead. A dense model uses all its parameters to produce every token. A mixture-of-experts model splits much of its parameters into groups called experts, and a routing step selects a small number of them for each token. The parameters actually used for a token are its active parameters.

    Dense model Mixture-of-experts model
    Memory needed All parameters All parameters, since any expert may be chosen
    Work per token All parameters Only the active parameters
    Speed Falls as the model grows Close to a much smaller dense model
    Example here gemma4:31b, 30.7 billion gemma4:26b, 25.2 billion total, 3.8 billion active

    The two Gemma models make a clean comparison: similar total size, similar memory, and about a threefold difference in speed. A 26-billion-parameter mixture-of-experts model still needs room for all 26 billion, because the router might pick any expert on the next token. What it saves is the work of reading them.

    Keep two questions apart: does it fit, which depends on total parameters, and how fast will it run, which depends on active parameters. See Chapter 11 and Chapter 5.

    What is an inference server, and how do Ollama, llama.cpp, and vLLM differ?¶

    An inference server is a program that loads a trained model into memory and answers requests to generate text from it. It owns the hard parts of running a model: placing the weights on the GPU, managing the KV cache, scheduling requests, and turning raw output into text. Everything else in the stack talks to the server and never to the model directly. A useful way to hold it in mind is as a loader plus an API: almost every problem is in one or the other.

    Server What it is Strength Cost
    Ollama A server with a model library and one-command downloads The quickest path from nothing to an answer Less control over scheduling
    llama.cpp A C++ engine for quantized GGUF models Runs almost anywhere, and is what Ollama is built on You build it and fetch models by hand
    vLLM A high-throughput server for Python and GPU deployments Many concurrent requests served efficiently The usual route on this hardware is a container

    This evaluation chose Ollama because it installs from one archive into a home directory, has the widest ready-made library, and offers an interface the harness can use directly. vLLM remains the candidate for a second pass on whichever model wins, because serving several sessions at once is the main lever for lowering cost per book. See Chapter 13.

    What is the difference between time to first token, tokens per second, latency, and throughput?¶

    They measure different parts of a request, and one "tokens per second" figure hides the difference.

    Metric What it measures
    Model load time How long the server takes to read a model from disk and get it ready; paid whenever the model is not already loaded
    Prompt processing speed How fast the server reads the prompt, in input tokens per second
    Time to first token Delay from sending a request to receiving the first token of the reply, mostly loading plus prompt processing
    Tokens per second Generation speed: output tokens per second once the reply has started
    Latency Total time for one request, from sending to receiving the last token
    Throughput Total work per unit of time across all requests in flight

    Reading is parallel and writing is sequential. A model reads an entire prompt at once but writes one token at a time, because each depends on the last. One model in this evaluation read a 30,000-token prompt in about ten seconds, roughly 3,000 tokens per second, so its time to first token was about ten seconds. A model reading 500 tokens per second would take a full minute.

    Latency and throughput pull against each other. For a single benchmark session, latency is what you feel and throughput is irrelevant, because only one request is in flight. For a service that generates many books, throughput sets the cost per book. See Chapter 15.

    What is an agent harness, and what is the agent loop?¶

    An AI agent harness is the program that wraps a language model so it can act. The model supplies language: given a conversation, it produces the next message. The harness supplies everything else: the system prompt that sets the task, the list of tools the model may call, the code that carries out those calls, the rules that allow or refuse them, and the bookkeeping that keeps the conversation going. Claude Code, OpenCode, Codex CLI, and Goose are harnesses.

    The agent loop is the cycle at its center:

    conversation = [system prompt, user request]
repeat:
    reply = model(conversation)
    if reply has no tool call:
        stop, the reply is the answer
    result = run the tool the reply names
    conversation += [reply, result]

    One trip around the loop is an agent turn. Four things follow from that sketch:

    1. The conversation only grows. The prompt of turn 40 contains everything in turns 1 to 39.
    2. Every turn pays the model's latency, in sequence.
    3. A single bad reply can end the run. If the model writes a tool call as plain text, the harness sees none and the loop stops.
    4. The model chooses the path. The harness never says which tool comes next.

    An agent is not a smarter model. It is an ordinary model inside a loop that feeds it the results of its own actions. Note the cost for a small model: Claude Code's own instructions and tool definitions run to about 19,000 tokens, written for Claude models, so a local model may struggle with that prompt and not with the task. See Chapter 16.

    What are the orchestrator, the harness, and the model, and why keep them separate?¶

    The evaluation has three roles, and its credibility depends on keeping them distinct:

    Role Fills it Where it runs May write benchmark content?
    Orchestrator A Claude Code session on a cloud model The laptop No
    Harness Claude Code in a container The DGX Only by calling the local model
    Model An open-weight model behind the endpoint The DGX GPU Yes, all of it

    The orchestrator starts work and coordinates it without doing it: it starts runs, watches them, and scores the results. The harness runs the agent loop and executes skills. The model is the only role that writes content. The rule that holds the evaluation together is that the orchestrator never writes benchmark content, because the question is whether a local model can.

    Because the harness is separate software from the model, the evaluation can swap the model underneath. The harness stays the same, a different model answers its requests, and any difference in the result belongs to the model.

    A subagent is an agent started by another to handle one part of a task in its own conversation, returning a summary, so its working detail never enters the parent's context. The chapter-content skill has a parallel mode that uses subagents, but the benchmark does not use it: each chapter is a separate harness run, so each has its own timing and token counts. See Chapter 16.

    What is an agent skill, and how does a harness choose and load one?¶

    An agent skill is a folder of instructions, and sometimes helper files, that teaches a harness how to carry out one kind of task well. A skill does not add a capability the harness lacks. It supplies the procedure for using the capabilities it has. Asked to "generate a learning graph", a model gives something plausible and unrepeatable. A skill pins down what a good learning graph is, how to build one, and how to check it, so the same request gives a comparable result each time.

    A skill is a directory with a shared layout: a SKILL.md file, a references/ folder of longer documents, a scripts/ folder of helper programs, and an assets/ folder of templates. The SKILL.md format is a Markdown file that opens with a YAML header carrying a name and a description.

    Skill loading works in stages so the context is not spent on instructions that are not needed:

    1. At startup, the harness reads only the name and description of each installed skill.
    2. When the model or the user's request selects a skill, the harness loads that skill's SKILL.md body.
    3. Reference documents load later still, one at a time, when a step names them.

    Skill installation is placing the skill directories where the harness looks for them. Here they live in one repository and are mounted read-only into the container, so the agent can follow a skill and cannot alter it.

    The description is how a skill gets chosen. A harness with thirty skills installed cannot read thirty full procedures on every request, so it reads thirty one-paragraph descriptions and loads the one that fits. A description should say both what the skill does and when to use it. See Chapter 17.

    What makes an evaluation design fair?¶

    A fair design changes one thing, holds everything else fixed on purpose, and records what it could not hold fixed. The independent variable is the one thing you deliberately change, so a difference in results can be attributed to it. Controlled variables are everything else that could affect the result, each one written down. Compare three designs for the same ten-model question:

    Design What varies What a difference can be blamed on
    Model only The model The model
    Model, context, and reasoning Three things together Any of the three, and you cannot say which
    Model, split across two units The model and the machine The model or the unit, and you cannot say which

    Only the first answers the question as asked. The second may be worth running as a second experiment about tuning, but its results must not be presented as a comparison of models.

    This evaluation controlled the course (one fixed Algebra I description), the workload (three skills, one prompt per stage), the harness, the server, the skills checkout, the hardware (DGX units of one configuration), the quantization, the fixed inputs (one course description and one prompt file per stage, kept in version control and copied fresh into every run), and the time limits. Each controlled variable is a promise, so each should have a line in the record that says what the value was and how you know.

    A reproducible experiment is one someone else can repeat from the record. Reproducibility is a property of the record, not of the result. See Chapter 19.

    What is the difference between a structural check and a quality judgment?¶

    A check answers a question that has a right answer, such as whether two concepts share a label. A judgment answers a question that does not, such as whether an explanation is clear. Checks can be automated and are fast. Judgments need a person, or a model whose own bias you have accounted for.

    Structural checks test the form of the output without judging its meaning. The learning-graph checks this project applies:

    Check What it tests A failure looks like
    Concept count The number of concepts equals the target 199 concepts when 200 were asked for
    Duplicate concept labels No two concepts share a label, ignoring case 40 of 200 labels duplicated
    Orphaned concepts Every concept has a prerequisite or a dependent 19 concepts connected to nothing
    Dependency cycle check No chain of dependencies loops back Three concepts each depending on the next
    CSV-JSON agreement The two files describe the same graph A concept in one and not the other
    Label length limit Labels are at most 32 characters A 64-character label that breaks the viewer

    An orphan is not the same as a foundational concept: a foundational concept has no prerequisites and does have dependents.

    Read a column of green checks as "nothing obviously broken", which is worth knowing and is not the same as "good". A graph can have no cycles and no duplicates and still be a graph of the wrong concepts. A scoring rubric is the written definition of what good means, by dimension, that makes the judgment repeatable. See Chapter 20.

    Why is generating a textbook a demanding test for a small model?¶

    It is not one hard task but a sequence of different ones, and a failure in any link breaks the next. The difficulty is also in the repetition. A model can follow any one rule when asked, so no single rule is the test. The test is whether it is still following all of them on sentence three thousand, long after it read the instructions.

    Each demand uses something a different ability:

    Demand What the model must do
    Structured output Write a learning graph as CSV and JSON that agree, with no cycles and no duplicate labels
    Long-form writing Produce about 55,000 words of prose that stays on topic and at the right reading level
    Command-line tool use Run shell commands, edit files, and run scripts through an agent harness
    Format precision Follow Markdown rules, such as the blank line before a list, and keep navigation entries valid
    A build that must pass Leave a site that survives a strict build
    Many turns of focus Stay on task across roughly 280 model turns, by this book's cost model

    A model that writes beautiful prose but breaks the JSON fails the first stage. A model that writes valid files but loses the thread after the fortieth tool call fails the third. That is why the benchmark reports per-stage results instead of one score. See Chapter 1.

    Why do models of different sizes run at very different speeds on the same machine?¶

    Generating one token requires reading the model's active weights from memory, so memory bandwidth, the number of bytes per second the memory can deliver, usually limits generation speed more than arithmetic does. A model that must read fewer bytes per token runs faster on the same machine.

    This evaluation measured the effect directly. A mixture-of-experts model that reads about 4 billion parameters for each token ran at 86 to 130 tokens per second. A dense model of about 31 billion parameters on the same unit ran at 28 to 40. The dense model reads roughly eight times as many weights per token and runs about three times slower, so speed does not fall in strict proportion. Bandwidth sets the ceiling, and other costs fill in the rest.

    Two lessons follow. First, a mixture-of-experts model's total size tells you what it costs in memory, and its active parameters tell you what it costs in speed, so keep the two questions apart: does it fit, and how fast will it run. Second, compare machines and models on measured tokens per second, not on CUDA core counts, because core count is a poor predictor of speed. See Chapter 5, Chapter 11, and Chapter 15.

    Can the Tailscale coordination service see my prompts?¶

    No. Tailscale separates two jobs that a conventional VPN combines. The coordination plane is the exchange of information needed to set up connections: who the devices are, their public keys, where they can currently be reached, and which may reach which. The data plane is the traffic itself: your commands, prompts, and a model's replies.

    The two use different paths. Coordination goes between each device and the coordination service. Data goes directly between the devices, encrypted by WireGuard, and does not pass through the service.

    Party on the path What it can see
    The laptop's router That encrypted packets go to a public address
    The coordination service Which devices exist, their public keys, and addresses
    A relay, if used Encrypted packets and the two endpoints
    The DGX's router That encrypted packets arrive from a public address
    The two devices Everything, because they hold the keys

    Think of the service as a mutual friend who tells two strangers each other's names and numbers and then leaves the room. It knows who talked to whom, and it never hears the conversation. The privacy of your prompts rests on the second half of that sentence. See Chapter 7.

    How do I estimate whether a model will fit before I download it?¶

    The memory estimation formula adds three parts, and the model-fit calculation then compares the total with the memory you have, after setting aside a safety margin:

    memory needed = weights + KV cache + runtime overhead
weights       = parameters × (effective bits ÷ 8)
KV cache      = context tokens × KV bytes per token

    Use about 5 effective bits for a file labeled 4-bit, because quantized files carry scaling factors and keep some layers at higher precision. Use about 3 GB for runtime overhead. Take the KV bytes per token from the model's shape, or use the chapter's illustrative 192 KiB if you do not know it. Then apply a safety headroom, 20% by default:

    Verdict Condition What to do
    Fits Needed ≤ memory × 0.8 Proceed
    Fits without headroom memory × 0.8 < needed ≤ memory Reduce context or choose a smaller file; do not run unattended
    Does not fit Needed > memory Choose a smaller model or lower precision

    For gemma4:31b (30.7 billion parameters) on a 128 GB unified-memory unit, the estimate is 28.6 GB at a 32,768-token context and 73.7 GB at 262,144 tokens, against a limit of 102.4 GB. Both fit, and both are within a few percent of what was measured.

    On unified memory, the memory to compare against is the RAM probe's available memory, not a GPU figure. And remember that the verdict predicts the starting footprint. A long run adds to it. See Chapter 11.

    Why is an agent turn slow even when the model generates quickly?¶

    Because an agent harness resends the whole conversation on every turn, and the turn overhead around the reply is easy to overlook, since no single request looks slow. A turn's time has three parts:

    T_turn = prompt tokens ÷ prompt speed + output tokens ÷ tokens per second + tool time

    Prompt caching is the server's remedy: it keeps the computed state for the part of the prompt that has not changed, so each turn reads only what is new. Prompt re-reading is the failure of that remedy, where the server recomputes most of the conversation each turn. Three cases, each with a 5-second tool:

    Case Prompt tokens read Reply tokens Turn time
    Caching works, dense model (3,000 read/s, 34 write/s) 2,000 600 23.3 s
    Re-reading, a slower model (500 read/s, 26 write/s) 55,000 600 138.1 s
    Caching works, fast mixture-of-experts model (3,000 read/s, 108 write/s) 2,000 600 11.2 s

    In the second case reading takes 110 of the 138 seconds, so tripling generation speed would barely change the turn.

    This was observed. With one model, the server restored a saved state just past the roughly 19,000-token system prompt on every turn and then re-read 46,000 to 65,000 tokens, taking one and a half to two minutes per turn. Over 55 tool calls that is about 83 of the stage's 102 minutes. A different model on the same server did not show it, and the cause was not identified.

    If one model is slow and another on the same server is not, search the server log for lines saying a context checkpoint was restored, and compare how many tokens each turn then processed. See Chapter 15.

    What does the Docker sandbox protect against, and what does it not?¶

    It is a filesystem sandbox, and in the arrangement this evaluation used it is not a network sandbox. Those are two separate boundaries.

    The container limits what the agent can read and write:

    Mount or setting What it grants What it prevents
    Run directory mounted at /work Read and write in this run's directory Touching any other directory on the host
    Skills folder mounted :ro Read the skills Changing a skill, so the test cannot be altered
    Non-root user in the image Ordinary file permissions Acting as root inside the container
    --rm The container is deleted when it ends Leaving a stopped container behind

    Build the image with your own user and group identifiers, so that files the agent writes belong to you and need no elevated rights to clean up.

    The network boundary is the gap. The harness container was started with --network host, so it could reach the model server, which listens only on the host's loopback address. A container on its own network cannot see the host's loopback. The cost is the network sandbox gap: a container in host network mode can reach anything the host can, including the internet and other machines on the tailnet.

    Options exist: a private network with the server on it too, a firewall rule that needs administrator rights, or no network at all, which cannot reach the model. Telling the agent not to reach out is not a boundary. See Chapter 18.

    Why do the three benchmark stages differ in how hard they are for a model?¶

    Because each one asks for a different capability, and a model that does one well can fail another. A pipeline stage is one skill run with defined inputs and outputs, and stage sensitivity is how much a stage's result depends on the model's capability. The stages are chained: each starts from the previous stage's output directory, so the work accumulates.

    Stage Skill Produces What it asks of the model
    1 learning-graph-generator 200 concepts, dependencies, taxonomy, learning-graph.json Dependency reasoning across 200 concepts, which punishes a model that cannot hold a structure in mind
    2 book-chapter-generator A directory and outline per chapter Assignment and ordering, where a small error in stage 1 becomes a failed dependency check
    3 chapter-content-generator, once per chapter The text of one chapter, added to the book so far Sustained, accurate prose at a stated level

    One model's results show how the stages differ in practice. For gemma4:26b on one DGX unit:

    Stage Produced Time
    1. Learning graph 200 concepts, 483 dependencies, 40 duplicate labels 6 minutes
    2. Book structure 14 chapters, 160 of 200 concepts assigned 4 minutes
    3. Chapter content 10 of 14 chapters written, 27,217 words 100 minutes in 14 runs

    Each row carries something a person would miss on a reading: stage 1's fault is 40 duplicate labels, stage 2 left 40 concepts unassigned which limits what stage 3 can write, and four of fourteen chapters were not written. Because stages chain, a failure in stage 3 can be a symptom of stage 2. See Chapter 21.

    How do I compute the cost per textbook from measured run times?¶

    Extrapolate from the stages you measured, then multiply by the cost of a generating hour. The benchmark covers three stages, which the Primary Author set at 10% of the cost of a whole book, because the learning graph, the chapter design, and the chapter content are about one tenth of the work. The rest is MicroSims, glossary, FAQ, quizzes, and references. The whole-book time estimate is:

    T_book = T_three stages ÷ 0.10

    For the reference model the three stages take 2.8 hours, so a whole book is about 28 hours of machine time. Then:

    generating hours per year  = 8,760 × utilization
cost per generating hour   = yearly cost ÷ generating hours per year
cost per book              = whole-book hours × cost per generating hour
cost per chapter           = cost per book ÷ chapters
books per year             = generating hours per year ÷ whole-book hours

    At 50% utilization there are 4,380 generating hours, and with a yearly cost of $8,275 each is $1.89. A 28-hour book costs $52.92, a 13-chapter book is $4.07 a chapter, and the unit makes 156 books a year. Energy for the book is 4.2 kWh, about 58 cents.

    The weak point is the 10%. It is an assumption about stages that have not been run. If the three stages were 5% of the book, the estimate doubles, and the cost per book goes from $53 to $106. State the assumption beside the number. See Chapter 22 and Chapter 6.

    Technical Detail Questions¶

    What is a strict site build, and why run one before every commit?¶

    A static site build, mkdocs build, turns the Markdown files into plain HTML, CSS, and JavaScript. A strict site build is the same build with every warning treated as an error, run with mkdocs build --strict. This book, and every book the benchmark generates, is built with MkDocs Material. An ordinary build prints a warning about a broken link and then finishes anyway, so a dead link ships. A strict build stops instead, and you fix the defect while the change is still small.

    $ mkdocs build --strict
WARNING -  Doc file 'index.md' contains a link 'chapters/02-setup/index.md',
           but the target is not found among documentation files.
Aborted with 1 warnings in strict mode!

    The wording above is abbreviated. A strict build also catches pages that exist on disk but are missing from the nav: block in mkdocs.yml, because those pages are built yet unreachable from the sidebar.

    Later in the book the same check becomes one of the objective measurements of whether a model's output is any good: a generated book that fails a strict build has a defect a program can find. See Chapter 1 and Chapter 21.

    What hardware does the DGX in this evaluation have?¶

    The evaluation used DGX Spark-class desktop units, and two units reported the same configuration:

    Component Reported value
    System DGX Spark-class desktop, aarch64
    CPU 20 Arm cores, 10 Cortex-X925 and 10 Cortex-A725
    Memory 128 GB unified, shared by the CPU and the GPU
    Storage 1 TB NVMe SSD
    GPU NVIDIA GB10, Blackwell architecture, 6,144 CUDA cores
    Operating system DGX OS 7.4 on Ubuntu 24.04
    Driver and compute NVIDIA driver 580, CUDA 13.0

    The most important fact in the table is what it leaves out: there is no separate GPU memory figure, because the GB10 combines an Arm processor and a GPU in one package and connects them to one pool of memory. The unit has one GPU, so multi-GPU concerns do not apply to it, and about 780 GB of the 1 TB drive was free after the operating system. The CPU core count of 20 matters less for inference, because the GPU does most of the arithmetic, than for tokenizing prompts, running the harness and its tools, and building the site.

    This is one unit's configuration, not a requirement of the course. See Chapter 5, and run the probes in Chapter 10 to learn what your own machine has.

    How do I check whether my DGX is x86_64 or aarch64?¶

    Run one command:

    uname -m

    On a DGX Spark-class unit it prints aarch64. On a typical rack DGX it prints x86_64. That single answer is the first branch of every setup.

    It matters because the two architectures, the x86_64 architecture of Intel and AMD processors and the aarch64 architecture of 64-bit Arm chips such as the GB10, are not compatible: a program compiled for one cannot run on the other without translation. Compiled Python packages are distributed as wheels built for one architecture and one operating system, and a download site chooses the right wheel by asking the machine what it is. On an aarch64 system, a package without an aarch64 build either fails to install or compiles from source, which is slow and sometimes impossible.

    Many install pages list an x86_64 file first, and a download that completes on an aarch64 machine will still fail when you run it. Pick the file whose name says arm64 or aarch64. If a tutorial written for x86_64 fails, find the aarch64 build, and do not retry the same command. See Chapter 5 and Chapter 8.

    How do per-token, subscription, and per-seat pricing differ?¶

    They differ in what makes the bill rise:

    Model The bill rises with Predictable? Fits best
    Per-token Tokens read and written Only if you can estimate tokens Variable, automated work
    Subscription Time Yes, up to the cap One user, steady use
    Per-seat People with access Yes Many users, light use each

    Per-token pricing charges for each unit of text the model reads or writes, usually quoted per million tokens with separate input and output rates. For textbook generation the bill follows the length of the conversation, because a harness resends a growing context on every turn.

    Subscription pricing charges a flat amount per period for access up to a usage limit. It suits steady individual use and makes a heavy job depend on the plan's cap.

    Per-seat pricing charges per person with access. It suits tools used by many people lightly, and it is a poor match for one automated pipeline that does a great deal of work through a single seat. See Chapter 6.

    What do MagicDNS, an access control list, and Tailscale SSH each do?¶

    They are three separate Tailscale features:

    • MagicDNS gives every device in a tailnet a name that resolves to its private address, so you type <dgx-host> and not 100.x.y.z. Names stay stable if the address changes, so a script written against the name keeps working. A short name resolves inside the tailnet, and the full name carries the tailnet's own name: <dgx-host>.<tailnet-name>.ts.net.
    • An access control list (ACL) is the tailnet's policy for who may reach what, kept by the tailnet's administrator. A minimal rule has an action of accept, a src for who may connect, and a dst for what they may reach and on which port. A device the list does not permit cannot connect, and sees no error beyond a timeout.
    • Tailscale SSH lets Tailscale itself handle SSH authentication using the tailnet identity instead of keys. It is turned on at the machine you log in to, with tailscale set --ssh, and that change belongs to the machine's administrator.

    This evaluation used none of the third. The DGX accepted ordinary OpenSSH logins over the tailnet, so key-based login was enough. Note that names and policy files are sensitive: the full machine name and the real ACL are on the list of things never to publish. See Chapter 9 and Chapter 23.

    Should I download a model as GGUF or safetensors?¶

    Pick the format that matches the server you will use:

    Safetensors GGUF
    What it is A format that stores tensors and nothing executable A single file holding weights, tokenizer, and metadata
    Typical precision 16-bit, sometimes quantized Quantized, often 4-bit or 8-bit
    Used by Python frameworks and servers such as vLLM llama.cpp and Ollama
    Why you would pick it You will serve with a Python framework You will serve with Ollama or llama.cpp

    This book serves with Ollama, so GGUF is the format you will meet, and pulling a model through Ollama's library gives you a file in the right format with its digests checked.

    The format has a cost that is easy to overlook. Two models in this evaluation were on disk in two formats, the standard one and one in the llama.cpp format, so each took twice its download size. The ten candidate models together took about 397 GB, a good part of a 1 TB disk. Before you collect a second format, check free space. See Chapter 12.

    How do I download a model and verify that the file is intact?¶

    Check the disk, download inside tmux, then compare checksums.

    1. Check free space against the largest file, not the average. Run df -h and compare the free space with the model's download size plus a margin for a second format. A 65 GB model on a disk with 60 GB free fails after an hour and leaves a partial file behind.
    2. Download inside tmux, so that a dropped SSH session does not stop it. For Ollama, one command pulls a named model and its quantization: ollama pull gemma4:31b.
    3. Verify the checksum. A checksum is a fixed-length value computed from a file's bytes, so any change to the file changes it. For a file you fetched directly, run sha256sum model.safetensors and compare the 64-character value with the one the publisher states. A mismatch means a corrupt or substituted file, and the right response is to delete it and download again. Ollama checks each layer's digest as it pulls, so for models fetched through it the verification is built in.

    Know where the space went. Ollama keeps models under ~/.ollama/models by default and the hub client under ~/.cache/huggingface, and both can be changed with an environment variable. Inspect them with du -sh, and remove what you no longer need with the server's own command, such as ollama rm <model>. See Chapter 12.

    What are temperature, top-p, and top-k?¶

    They are sampling parameters: the settings that control how the next token is chosen from the model's probabilities.

    • Temperature scales how adventurous the choice is. A temperature of 0 always takes the most likely token, so output is repeatable. Higher values spread the choice, so output varies from run to run.
    • Top-k limits the choice to the k most likely tokens.
    • Top-p limits the choice to the smallest set of tokens whose probabilities add up to p.

    They matter for two reasons. First, they change the output, so a benchmark must fix and record them, or its runs are not comparable. Second, they interact with reasoning models, where a high temperature can lengthen a chain of thought.

    They do not make a model faster. If you are looking for speed, look at quantization, context length, keep-alive, and prompt caching instead.

    See Chapter 15 for the settings and Chapter 3 for why a model's output varies at all.

    What placeholders and address ranges should I use in examples?¶

    A login name <user>
    An administrator's account <admin>
    The tailnet's name <tailnet-name>.ts.net

    Redaction is replacing a detail in a specific artifact with a placeholder or removing it, and sanitized sample output is the result: it shows the format and meaning and none of the identifiers. For example, a raw status line becomes 100.x.y.z <dgx-host> <admin>@ linux active; direct 198.51.100.7:41641: the address became the placeholder, the full name became the machine placeholder, the account became the administrator placeholder, and the remote endpoint was replaced with an address from a documentation range.     How does a concept's impact score decide how many words it gets?¶

    Each concept gets its own word-count target instead of one flat number per chapter. First the CIS is normalized against the largest CIS in the whole book, using a logarithm, because CIS is heavy-tailed and a straight proportion would crush most concepts to nearly zero. The result is the elaboration score E:

    E(c) = ln(CIS(c) + 1) / ln(CIS_max + 1)

    Then E maps to a tier:

    Tier E range Target words Required elements
    A 0.5 or more 500 to 750 A worked example and a diagram, chart, table, or MicroSim
    B 0.2 up to 0.5 250 to 400 A worked example
    C under 0.2 120 to 200 A clear definition

    In this book CIS_max is 2,518. Concept Dependency has a CIS of 36, so E is ln 37 / ln 2519, about 0.46, which is tier B and just under the tier A line. Anti-Padding Rules has a CIS of 1, so E is about 0.09, which is tier C. A chapter's length is the sum of its concepts' targets, and a chapter with several tier A concepts runs longer on purpose. The table of targets is a guideline, not a quota. See Chapter 2.

    Why does nvidia-smi report my GPU's memory as "Not Supported"?¶

    Because there is no separate GPU memory to report. On a unified-memory machine such as the GB10, "GPU memory" and "system memory" are two names for one pool, so nvidia-smi has no GPU-only figure to print. Not Supported in the memory column is the signature of unified memory, not a fault in the driver.

    The rest of the nvidia-smi output is normal. In the abbreviated, sanitized example below, the first line holds both versions that matter, and the GPU shows a low performance state and a few watts because it is idle:

    | NVIDIA-SMI 580.xx.xx    Driver Version: 580.xx.xx   CUDA Version: 13.0 |
|   0  NVIDIA GB10          On  | 44C   P8    4W / N/A      | Not Supported |

    Read the memory use from the system side instead, with free -h. Chapter 10 builds that fallback into the memory probe, so the report still returns a total and an available figure on this machine. A probe that treats Not Supported as zero would report a machine with no memory, which is why it should record null for anything it could not read. See Chapter 5.

    What is the difference between the NVIDIA driver version and the CUDA version?¶

    They are two layers, and the driver sets a ceiling for the other. The NVIDIA driver is the software that lets the operating system and programs talk to the GPU. The CUDA runtime is the set of libraries a program is built against, and it ships inside the programs that use it. The "CUDA Version" that nvidia-smi prints is the newest runtime the installed driver can support. It is not the version of any toolkit installed on the machine.

    The rule that follows is that a program's CUDA build must be at or below the driver's ceiling. This machine's driver 580 supports CUDA 13.0, so a framework built for CUDA 12.8 runs, and one built for CUDA 13.2 does not. Updating a driver needs administrator rights, so on a machine you do not administer, the practical fix is to choose a framework build at or below the driver's version.

    When a program reports "no CUDA device" or "driver too old", run nvidia-smi first. If it lists the GPU and a driver version, the driver works, and the fault is in what is built on top of it. See Chapter 5 and Chapter 8.

    How much electricity does a DGX use to generate a textbook?¶

    Electricity cost is the energy the system consumes times the price of that energy. The cost analysis assumes 150 W while generating, 40 W while idle, and $0.1385 per kWh. The idle power draw matters because a machine used half the time idles the other half, so the yearly energy has two terms:

    generating hours per year = 8,760 × 0.50 = 4,380
idle hours per year       = 4,380

energy = (4,380 h × 150 W + 4,380 h × 40 W) ÷ 1,000 = 832 kWh
cost   = 832 kWh × $0.1385 per kWh = $115

    For one book, a whole generation of about 28 hours at 150 W uses 4.2 kWh, or about $0.58. That is the only variable cost of local generation.

    The assumption is deliberately high. A published review measured 60 to 90 W for many model workloads on this class of machine and just under 200 W at the most, and this evaluation's own logging read 69 W from the GPU at 92% utilization during one run.

    Teams often worry about the power bill of a GPU machine and then find it is about a hundred dollars a year. Do the sum before the meeting. The real cost drivers are almost always the labor and the hours the machine sits unused. See Chapter 6 and Chapter 5.

    How does utilization change the cost per book?¶

    Utilization rate is the share of available time the machine spends doing useful work, and it is the lever that fixed costs ride on. The same $8,275 spread over more books gives a lower cost per book. The cost analysis assumes the unit generates for 50% of the hours in a year, which allows for waiting, failed and repeated runs, and maintenance.

    Utilization Books per year Cost per book
    75% 235 $35
    50% (reference) 156 $53
    25% 78 $105
    10% 31 $263

    At 50% utilization the unit generates for 4,380 hours a year, so each generating hour costs $8,275 ÷ 4,380, about $1.89. A book that takes 28 hours of generation then costs about $53.

    At 10%, the machine is a bad purchase for this job. The cost does not rise because the machine got worse. It rises because the same fixed cost is shared among a fifth as many books. So before you buy hardware for a pipeline, estimate how many books you will honestly generate in a year. See Chapter 6.

    How does key-based SSH login work, and is a passphrase-free key risky?¶

    An SSH key pair is two linked files: a private key that stays on your machine and a public key that you give to servers. A server holding your public key can check that you hold the matching private key without the private key ever crossing the network, and the check cannot be guessed by trying passwords. Create a modern Ed25519 key with ssh-keygen -t ed25519, which writes id_ed25519 (private) and id_ed25519.pub (public) to ~/.ssh. Then ssh-copy-id <user>@<dgx-host> logs in once with your password and appends the public key to the server's authorized_keys.

    A passphrase encrypts the private key file on disk. A passphrase-free key lacks that protection, so the file alone is enough to log in. That is what makes unattended login possible, since a script or an agent cannot type a passphrase. It is a trade, made knowingly in this evaluation.

    The price is that the private key file is as sensitive as a password. Anyone who copies it can log in as you from anywhere, with nothing to guess. Keep it only on the machine that needs it, never commit it to a repository, and tell the administrator that you installed a key so they can remove it when the project ends.

    Test the key with ssh -o BatchMode=yes <user>@<dgx-host> hostname. BatchMode makes the client fail at once if it would need a password, so a broken key cannot hide behind a password fallback, and a script fails in a second instead of hanging. Permission denied means the key is not installed or is not the one the client offered. See Chapter 7.

    How do I reach a model server that listens only on the DGX's loopback address?¶

    Use an SSH port forward. It carries traffic for one network port through an SSH connection, so a service on the remote machine appears as though it were on your own. A server bound to the DGX's loopback address cannot be reached by any other machine, and a forward makes it reachable from the laptop without opening anything on the network.

    ssh -N -L 11434:127.0.0.1:11434 <user>@<dgx-host>

    The command has three parts. -N tells SSH not to run a remote command and only hold the tunnel open. -L creates the forward in the form local-port:destination:destination-port. The destination is resolved on the remote side, so 127.0.0.1 there means the DGX itself.

    While the command runs, a request to port 11434 on the laptop reaches the model server on the DGX, and the traffic travels inside the encrypted SSH connection. Port 11434 is the default port of the Ollama server that Chapter 13 sets up.

    This is the cautious way to share an endpoint, because the server stays closed to everything except the person holding the forward. See Chapter 7.

    What is the difference between environment.yml and requirements.txt, and conda and pip?¶

    An environment.yml file is the specification of a conda environment: it names the environment, lists the channels in order, and lists the packages with pins where you want them. A requirements.txt file is pip's equivalent: Python packages one per line with optional version pins, created by pip freeze and installed with pip install -r requirements.txt.

    name: dgx
channels:
  - conda-forge
dependencies:
  - python=3.12
  - tailscale
  - tailscaled

    The difference is scope. pip installs only Python packages from the Python Package Index. Conda installs Python itself, non-Python libraries and programs such as Tailscale, and Python packages, from channels such as conda-forge.

    The rule that avoids most trouble: install with conda first, use pip only for what conda lacks, and run the pip installs last. Going back and forth lets pip replace a package conda installed, and conda's record is then wrong about what is present.

    Two details make a specification reproducible. Always name the channel, because an unnamed one falls back to whatever a machine has configured. And pin the interpreter: python=3.12 fixes the major and minor version, and a year-later rebuild without a pin gets a newer Python that may lack wheels for packages you use. See Chapter 8.

    How do I test the connection to the DGX in layers?¶

    Use the three-step connectivity test, in order, because each step proves something the previous one did not:

    Step Command What it proves
    1 tailscale status The device is listed and its state is not offline
    2 tailscale ping <dgx-host> Packets reach the device, and which path they take
    3 ssh -o BatchMode=yes <user>@<dgx-host> hostname The login works with a key, with no prompt

    A failure tells you which layer to inspect. Step 1 failing points to your daemon or your account. Step 2 points to the network path or the access rules. Step 3 points to the SSH server or your key.

    Learn to read the last column of tailscale status. A dash marks this device, active; direct means data is flowing over a direct path, active; relay means traffic goes through a relay, idle means connected with nothing in flight, and offline with a time means the device has not been reachable. A ping that first goes through a relay and then switches to a direct address is NAT traversal happening in front of you. See Chapter 9.

    How do I get access to a DGX that belongs to someone else?¶

    There are two arrangements, and they differ in what you become:

    Tailnet invitation Node sharing
    You become A member of their tailnet A guest with access to one device
    You can see Whatever the access rules allow Only the shared device
    Whose policy applies Theirs Theirs, for that device
    Good for A team working on shared machines Giving one outsider temporary access

    A tailnet invitation adds you to the administrator's tailnet, which is how this evaluation was set up: the machine's administrator invited the Primary Author, and both units were already members. Node sharing shares one device into your own tailnet without making you a member of theirs.

    A third thing is easy to confuse with both. A Tailscale auth key is a pre-generated credential that lets a device join a tailnet without a person signing in through a browser, for machines nobody sits at. It is equivalent to a password for joining the network. Never put one in a repository, a chat, a screenshot, or a log, and prefer a key that expires soon and works once. An evaluator who is a guest of someone else's tailnet usually does not need one. See Chapter 9.

    How does the probe report tell me which setup steps to follow?¶

    Through hardware variation branching: choosing the next setup step from the report instead of from assumption. A short function reads the JSON report and returns the branches that apply:

    • The CPU architecture selects aarch64 or x86_64 packages.
    • No GPUs in the report means CPU only.
    • unified_memory true means size models against system RAM.
    • More than one GPU means plan to split across GPUs.
    • Otherwise, size models against one GPU's memory.

    The unified-memory branch is the one that surprises people. On a discrete-GPU server, the usable model size is the GPU's free memory. On a unified-memory machine, the GPU's memory fields come back as null, the probe sets unified_memory to true, and the figure to use is the RAM probe's available_gib, minus the headroom that Chapter 11 introduces.

    Note that the two null GPU memory values are not an error. They are the unified-memory signature. A report that shows them also shows the architecture, which is why the same report drives both the package choice and the sizing rule. See Chapter 10.

    What is a gated model, and how should I handle the access token?¶

    A publisher gates a model when you must be signed in and accept its terms before the files can be downloaded. Gating is the publisher's way of recording who agreed to its license. A gated download needs an access token, a credential that identifies your account to the hub.

    Treat the token as a secret:

    • Keep it in an environment variable or the tool's credential store, not in a script.
    • Never commit it, paste it into a chat, or let it appear in a log or a screenshot.
    • Prefer a token limited to read access.
    • Revoke it when the project ends.

    The reason is the same as for SSH keys and Tailscale auth keys: this book's repository is public, and a token committed once is exposed for good. Tokens are one of the categories of detail that must never be published, which Chapter 23 treats in full.

    Before you download any model, gated or not, also do a license review: read the license file, not just the page metadata, because they can disagree. Ask whether you may use the model for your purpose, whether you may redistribute what it generates, and whether any conditions apply, such as a revenue threshold. See Chapter 12.

    How do I install and run Ollama on a DGX I do not administer?¶

    Use a user-space installation from a release archive, and run the server in tmux. The usual instructions run an installer with sudo and create a system-wide service, which is a step you should not take on a machine that belongs to someone else.

    1. Download the pinned release archive for the machine's architecture (arm64 for aarch64).
    2. Compare its SHA-256 with the published value, and stop if they differ.
    3. Unpack it under your home directory.
    4. Start the server in a detached tmux session, bound to the loopback address, with its output going to a log file.
    tmux new-session -d -s ollama \
  "$HOME/opt/ollama/bin/ollama serve > $HOME/opt/ollama/serve.log 2>&1"

    Two environment variables shape the server. OLLAMA_CONTEXT_LENGTH sets the context window in tokens, which is a memory reservation. OLLAMA_KEEP_ALIVE sets how long an idle model stays loaded; by default it is unloaded after about five minutes, and the next request pays the load time again.

    The trade-offs are explicit. Removing the server is deleting one directory, but it is not a system service, so a tmux session does not survive a reboot and the server is simply not running until someone starts it. Check it with tmux has-session -t ollama. See Chapter 13.

    How do I send a first prompt to a local model?¶

    Ollama's local API endpoint is http://127.0.0.1:11434, and it offers an OpenAI-compatible API, so any client written for that service works by changing only the base address. The main route is the chat completions endpoint:

    curl http://127.0.0.1:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "gemma4:31b", "stream": false,
       "messages": [{"role": "user", "content": "Reply with the single word: ready"}]}'

    -H adds a header telling the server the body is JSON, -d supplies the body, and "stream": false asks for the whole reply at once. The reply is a JSON object: the text is at choices[0].message.content, and a usage block reports prompt_tokens and completion_tokens, which are the two numbers every later performance measurement uses.

    A first-prompt smoke test sends one tiny request and checks four things: the server answered, the reply is not empty, the speed is plausible, and the model is running on the GPU. Make it a repeatable check by capping max_tokens and dividing output tokens by elapsed seconds. A curl request removes every layer between you and the server, so a failure there is a failure of the server or the model, not of your program. A Python client makes the same request from code, and a version that uses only the standard library runs on a fresh machine with nothing installed. See Chapter 13.

    What does a reading-level score tell me about a generated chapter?¶

    A reading level measure estimates the school grade needed to read a text from the lengths of its sentences and words. The common one is the Flesch-Kincaid grade, which a script computes, so it is cheap and repeatable. The same statement about a line's slope, correct both times, scores 15.2 when written as "The slope of a linear function quantifies the rate at which the dependent variable changes relative to the independent variable" and 7.1 when written as "Slope is a number that describes how steep a line is. You calculate it by dividing the vertical change between two points by the horizontal change between them."

    It measures form and nothing more. A passage can score at grade 10 and be nonsense, and a clear explanation can score high because it uses necessary technical terms. Its right use is as a flag: a chapter written for adults that scores at grade 4 is probably padded with short sentences, and one at grade 20 is probably unreadable.

    It is also one input, not a verdict. The book's Chapter Quality Score appendix describes the program that scores each generated chapter from 0 to 100 on six weighted dimensions: budget, diagram placement, diagram specification, format, padding, and reader fit, which is where reading level counts. Read it as a screen that points to chapters worth reading, a conformance score and not a quality verdict: it does not check that the mathematics is correct or that the explanation is any good.

    The same warning applies to any single number. One score hides the profile of where a chapter is strong or weak. See Chapter 20.

    How does the benchmark decide that a stage or a chapter is finished?¶

    By a stated criterion, not by the model's own announcement. A model that says it is done has told you what it believes, and the criteria tell you what happened.

    For a chapter, the chapter completion criterion is that its placeholder text is gone and it has at least 1,000 words. A model that announces it is running a skill and ends its turn without writing anything has not written a chapter, and the criterion catches it.

    For a stage, required output files must exist. The learning-graph stage has seven: the concept list, the dependency graph as CSV and as JSON, the concept taxonomy, a quality-metrics report, a taxonomy-distribution report, and an index page. The navigation entries in the site configuration must also make the new pages reachable, because a page missing from the navigation is invisible to readers and a strict build can fail on it. Several models left the entries out even when they wrote the files, which is why it is a check of its own.

    Per-stage metrics are then computed the same way for every run. Skill completion rate is stages that ended on their own with every required file, divided by stages attempted. Build success is a strict site build that exits with no errors. Write these definitions down before the first run, so the argument about whether a run that built with warnings counts happens once. See Chapter 21.

    How do I fetch run output from the DGX, and can I publish it?¶

    Use a script that copies with rsync, which transfers only new and changed files and never deletes, and that takes the host list from an environment variable so that no address is written into the script:

    export DGX_HOSTS="<user>@<dgx-host-a> <user>@<dgx-host-b>"
src/orchestration/fetch_runs.sh --watch 300

    With --watch it fetches again every 300 seconds and stops when a book or a phase finishes, when a host that was answering fails twice in a row, or when no run is going. The last two conditions are the useful ones: a unit that has frozen announces itself by failing to answer.

    The fetched output is not safe to publish. It holds local paths and, in the run event streams, whatever the commands printed. Keep it outside the repository, which is raw output isolation, and publish only through a narrow script that copies a model's learning graph, its chapter text, and the course description, and leaves out any file with an address, a host name, or a home-directory path.

    Once the output is on the laptop, preview the generated book as a reader would: it is a project like any other, so mkdocs build --strict builds it with no need to reach the DGX. And fetch each model's results as it finishes, so a unit that freezes does not take unfetched results with it. See Chapter 21 and Chapter 23.

    How do I redact a screenshot of a terminal or an admin console?¶

    A screenshot carries more than the lines you meant to show: window titles, tab names, a browser's address bar, a prompt that includes the username and hostname, and a sidebar listing every other machine. Three rules cover most of it:

    1. Crop first, to the smallest region that makes the point, so most of the window never enters the file.
    2. Cover with a solid fill, not a blur, because a blur can be partly reversed.
    3. Check the result at full size, including the edges, since a prompt line at the very bottom is easy to miss.

    Count the screenshot as an artifact in the publication safety review. The review's checklist includes "every screenshot has been cropped, covered, and checked at full size", and it is the kind of check that does not depend on a pattern, so it needs a person. See Chapter 23.

    How do context truncation and compaction differ?¶

    The conversation only grows, so context management has to shrink it before it reaches the model's window. Peak context size is the largest the conversation reached in a run, and it tells you whether a window was big enough.

    Context truncation Context compaction
    What it does Drops the oldest content Asks the model to summarize the earlier conversation into a short note and replaces the old content
    What it keeps The recent turns The thread, minus detail
    What it costs Nothing, but it is crude A model call
    Risk The beginning, which holds the task, is exactly what disappears A summary can drop a detail that mattered

    The dangerous interaction is with the server's window. Claude Code assumes a window of about 200,000 tokens. If the server was configured with a smaller one, the server truncates silently before the harness knows to compact, and the model loses the start of its own task without any message. Measurements show how real this is: two stages in this evaluation peaked at 135,000 and 147,000 tokens, and a 128,000-token window would have cut both off.

    That is why the evaluation raised the server's context setting to a large value, and why raising it has a memory cost, as Chapter 11 showed. Check the peak context of a run before concluding that a model "lost the task". See Chapter 16.

    How do I point Claude Code at a local model?¶

    With environment variables, because Ollama offers an Anthropic-compatible API. A local endpoint connection points the harness at your own server instead of the vendor's, and the set this project's runner uses is:

    Variable Value Purpose
    ANTHROPIC_BASE_URL http://127.0.0.1:11434 Send requests to the local server
    ANTHROPIC_AUTH_TOKEN A placeholder word Satisfy the harness without a real credential
    ANTHROPIC_API_KEY Empty Make sure no real key is used
    ANTHROPIC_MODEL and the DEFAULT_*_MODEL variables The local model's tag Use the same model in every role
    CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC 1 Turn off optional network features
    API_TIMEOUT_MS A large value Allow a slow model a long time per request
    CLAUDE_CODE_MAX_OUTPUT_TOKENS 32000 Allow long replies without cutting them off

    Then run a stage headlessly:

    claude -p --model <model> \
  --output-format stream-json --verbose \
  --max-turns 150 --dangerously-skip-permissions \
  < prompt.txt > run.jsonl

    -p runs non-interactively, --output-format stream-json --verbose writes every message, tool call, and result as a line of JSON, and --max-turns stops a confused model from running forever.

    Be exact about what Claude Code is doing here: it is the agent loop and nothing more. Every token of the textbook comes from the local model, and the placeholder credential means the harness could not reach Anthropic's service even if it tried. The last flag lets the agent run any command without asking, which an unattended run requires, and it is acceptable only inside a sandbox that limits the agent to its own run directory. Other harnesses, such as OpenCode, Codex CLI, and Goose, read the same skill format. See Chapter 17 and Chapter 18.

    Common Challenges Questions¶

    Does a model with more parameters always write better?¶

    No. Parameter count tells you what a model costs to hold and run. It does not tell you how well it writes or follows a skill, and a smaller model can outperform a larger one on a given task. Treat the number as an input to the memory calculation and let a measurement decide quality.

    Parameter count drives two practical quantities. The first is memory: every parameter must be held in memory, so more parameters means more memory, a conversion Chapter 11 performs exactly. The second is work per token: a model with more parameters generally does more arithmetic for each token and so, other things equal, generates more slowly.

    The first benchmark round shows the same thing. A 30-billion-parameter model wrote every chapter it planned, while the 117-billion-parameter gpt-oss:120b wrote six of its ten, and a 128-billion-parameter model ran at 3 tokens per second and left no room for a 64,000-token context. Size predicts cost. Only a test predicts quality. See Chapter 3, and the Evaluation Status page for the current table.

    Why does my Markdown list render as one run-on paragraph?¶

    MkDocs does not start a list unless a blank line comes before it. A list typed straight after a sentence collapses into one paragraph. The page still builds with no error, which is why the problem goes unnoticed. Always leave one empty line before the first bullet or number, and the same goes for tables.

    Wrong:

    The commands you need are:
- pwd
- ls

    Right:

    The commands you need are:

- pwd
- ls

    Because the build gives no warning, a strict build will not catch this. Skim the rendered page after you write a list. This is one of the Markdown rules that textbook generation tests, since a model has to follow it every time it writes a list across tens of thousands of words. See Chapter 1.

    A download finished but the program will not run on my DGX. What went wrong?¶

    The most likely cause is an architecture mismatch. Download pages often offer the x86_64 build first, and a file built for x86_64 will download perfectly on an aarch64 machine and then fail when you run it, typically with an "Exec format error" or a similar message about the executable.

    Check the machine, then the file, using standard Linux tools that are not specific to this book:

    uname -m
file ./the-downloaded-program

    If the machine says aarch64 and the file says x86-64, you have the wrong build. Retrying will not help. Go back to the download page and pick the file whose name says arm64 or aarch64, or use a package channel that publishes aarch64 builds, as conda-forge does.

    The same mismatch appears inside Python as a package that either fails to install or starts compiling from source, which is slow and sometimes impossible. If a package has no aarch64 wheel, check whether a conda-forge build exists before you try to compile. The two cheap habits are to run uname -m before downloading anything, and to record the architecture in the report your probes write. See Chapter 5 and Chapter 8.

    tailscale status says it cannot connect to the daemon. What do I do?¶

    The cause is almost always that tailscaled is not running. The client program you type commands into only talks to the Tailscale daemon, the background process that creates the network interface, holds the encryption keys, and maintains the connections. If the daemon is not running, the client has nothing to talk to, and the error looks like a broken network.

    The usual reasons are that the daemon does not survive a reboot, or that you started it in a terminal tab that you later closed. Restart it in its own tab before suspecting the DGX, the router, or your account:

    sudo "$CONDA_PREFIX/bin/tailscaled"

    Give sudo the full path to the binary, because sudo discards the conda PATH. Leave that tab open and running. Then, in a second tab with the environment activated, run tailscale status again.

    Creating a network interface requires administrator rights on the laptop, which is why the daemon is started with sudo. Tailscale installation here means the open-source client, tailscale, and its daemon, tailscaled, installed together into the dedicated dgx conda environment with conda create -n dgx -c conda-forge tailscale tailscaled. Keep both at the same version, since the client does nothing without the daemon. See Chapter 9.

    Why is the first request to a model so slow?¶

    The first prompt after a model is unloaded pays for model loading: reading the file from disk into memory and preparing it to run. Its duration is the file size divided by the drive's storage read speed, so a 20 GB file at 2 GB per second takes about 10 seconds, and the same file from a hard drive at 0.15 GB per second takes over two minutes. If you compute tokens per second from that first request, the number looks terrible, and it is not the model's speed.

    Send the prompt twice and read the speed from the second. If the second is also slow, the cause is the model, the context, or the memory, and not the load.

    Two server behaviors are worth knowing. By default a model is unloaded after about five minutes without a request, so a benchmark that sends prompts minutes apart pays the load again unless you raise the keep-alive. And ollama ps shows what is loaded and how much memory it holds, so you can tell whether the model is currently resident.

    When you report speed, state whether the figure includes a load. A benchmark that mixes load time into every generation measurement will understate the machine by a wide margin. See Chapter 13 and Chapter 15.

    How can I tell whether a learning graph's edges point the wrong way?¶

    Read the list of foundational concepts, the ones with no prerequisites. They should be plain, introductory terms. In this book that list is Command Line Basics, Python Scripting Basics, Git Version Control, Generative AI Assistant Use, Markdown Source Files, Bloom's Taxonomy, Open-Source License, Privacy, CPU Architecture, System RAM, GPU, and Storage Capacity.

    If you read an edge backwards, every prerequisite becomes a follow-on topic and the whole ordering silently inverts. A graph built that way would put terms like "Evaluation Report" on the foundational list, and the mismatch is easy to spot once you know to look. If an advanced term shows up there, the direction is wrong.

    Remember the convention: an edge points from the dependent concept to its prerequisite, so MicroSim → Intelligent Textbook reads "a MicroSim needs the idea of an intelligent textbook". You can also open the learning graph viewer, search for a concept, and click it to see its prerequisites and dependents. See Chapter 2 and the Learning Graph page.

    Which setup steps need administrator privileges, and what can I do without them?¶

    Administrator privileges are the right to change system-wide settings: install software for all users, change the driver, open network ports, and manage accounts. On Linux that means root access, usually through sudo. A standard account has none of it, and in this evaluation the benchmark account had none.

    Action Needs administrator privileges? What this evaluation did
    Install a model server for one user No Unpacked a release archive into the home directory
    Install a system package Yes Avoided it, or asked the administrator
    Use Docker Yes, via group membership The administrator added the account to the group
    Change the NVIDIA driver Yes Never attempted
    Restart a frozen machine Yes, or physical access The administrator did it

    Two practical points follow. First, almost everything you need can be installed into your home directory, which is why this book installs the model server from a release archive. Second, membership in the docker group is equivalent to administrator access on that machine, so it is a decision only the administrator can make, and each such request has a delay.

    A system administrator is the person responsible for a machine's configuration, security, and availability, and their administration time is a cost too, even when no invoice is sent. A cost model that counts only your own hours understates the work. See Chapter 6 and Chapter 18.

    SSH warns that the server's host key has changed. What should I do?¶

    Stop and do not accept it. The client stored the server's key in known_hosts the first time you connected and checks that the server presents the same key every time. If the key suddenly differs, the client refuses to continue and prints a loud warning, because the check exists to protect against someone placing themselves between you and the server.

    The warning has two ordinary causes and one serious one:

    • The machine was reinstalled, so it generated a new key.
    • Its disk image was cloned onto another machine.
    • Something is intercepting the connection.

    You cannot tell which from the warning alone. Compare the fingerprint the client shows with a value the machine's administrator gave you through another channel, and not through the same connection you are trying to verify. A fingerprint is useful only if you compare it with an independently supplied value.

    If the administrator confirms a reinstall, the usual SSH remedy is to remove the old entry from known_hosts and connect again. If they cannot confirm one, do not proceed. The same discipline applies on the first connection: compare the fingerprint before you answer yes. See Chapter 7.

    Why does conda activate fail inside a script or an agent?¶

    The conda activate command is a function defined by your shell's startup files, so it exists in an interactive shell and may not exist in a non-interactive one. A script, a cron job, or an agent running a command can fail with a permission error or "command not found" even though the same line works when you type it.

    Two fixes avoid activation entirely:

    # Call the environment's executable by its full path
<conda-prefix>/envs/dgx/bin/tailscale status

# Or let conda run one command inside the environment
conda run -n dgx tailscale status

    The same family of problem shows up with sudo, which discards the conda PATH. To start the Tailscale daemon, which needs administrator rights on the laptop, give sudo the full path to the binary: sudo "$CONDA_PREFIX/bin/tailscaled".

    Both failures have one cause: the shell does not have the environment's directory on its path, because activation never ran in that shell. Calling the executable by its full path makes the dependency explicit and removes the problem. Reserve conda activate for terminals you type into. See Chapter 8 and Chapter 9.

    PyTorch imports without error. How do I know it can use the GPU?¶

    Importing proves nothing. The default install on some platforms is a CPU-only build of PyTorch, and it imports without any error, so a missing GPU shows up only when you ask. Two lines establish which build you have:

    import torch
print(torch.version.cuda)          # for example '13.0'; None means a CPU-only build
print(torch.cuda.is_available())   # True only if the driver and a GPU are usable

    The first prints the CUDA version the build was compiled for, which is None for a CPU-only build. The second asks whether a GPU is usable right now.

    Read the pair together with nvidia-smi:

    • If nvidia-smi lists a GPU and is_available() is False, the driver is fine and the problem is the PyTorch build or its CUDA version. Reinstall a CUDA-enabled build at or below the driver's CUDA version, and on an aarch64 machine check that one exists for aarch64.
    • If nvidia-smi itself fails, fix the driver layer first.

    Make torch.cuda.is_available() part of every environment rebuild check. A model that silently runs on the CPU looks like a performance problem when it is really an install problem. See Chapter 8 and Chapter 10.

    Why is the DGX missing from my device list or offline?¶

    Four causes produce this symptom:

    1. You signed in with the wrong account. Tailscale authentication binds your device to the identity you sign in with, so signing in with a different account than the one the administrator invited creates or joins a different tailnet, and the DGX will not appear. If the listing shows only your own laptop, compare the account on the sign-in page with the one the invitation was sent to.
    2. Your daemon stopped. If tailscale status cannot reach the daemon, restart tailscaled in its own tab.
    3. The device key expired. A device's credentials last 180 days by default, and a machine not used for months may have silently dropped off the network. The first sign is a device that shows as offline with no other explanation. The fix is to sign in again from that device, and for a machine you do not sit at, to tell the administrator.
    4. The access control list does not permit you. A device that is in the tailnet but not allowed by the policy simply cannot connect, and the only symptom is a timeout. Only the tailnet's administrator can change the policy.

    The three-step connectivity test narrows it. A failure at step 1, tailscale status, points to your daemon or your account, and an expired key shows up there too, as a device listed as offline. A failure at step 2, tailscale ping, points to the network path or the access rules. See Chapter 9.

    ollama ps shows under 100% on the GPU. What does that mean?¶

    Part of the model is running on the CPU, and it will be much slower than the figures in this book. GPU offload places the model's layers on the GPU so the GPU does the work, and the ollama ps command shows what is loaded, how much memory it holds, and the share on the GPU.

    On a unified-memory machine every layer is normally offloaded, because the memory is shared. A share below 100% usually points to a context setting so large that the cache and the weights no longer fit together. The server then keeps some layers off the GPU to stay within memory.

    Work through it in order:

    1. Check the configured context length. Reduce OLLAMA_CONTEXT_LENGTH to the smallest value the job needs and restart the server.
    2. Re-run the fit calculation from Chapter 11 with the context you actually configured, and compare with available memory.
    3. Check what else is resident. Another loaded model, a container, or a build can be holding memory the weights need.
    4. Read the server log for the load line, which reports how much memory the model requested.

    If the share returns to 100% after you lower the context, the diagnosis was right, and the cost was the long context. See Chapter 13.

    My model was fast in a short test but slow in a long run. Why?¶

    A short test finishes before the chassis has warmed and before the cache has grown, so the first number was never the machine's real speed. Two things can slow a long run with no change in the workload:

    • Thermal throttling. Thermals are the temperatures a system reaches and how it manages them. As a chip heats up, it reduces its own speed to stay below a safe temperature. It shows up as a speed that falls over a long run while the temperature climbs, and it is invisible in a short test.
    • Memory pressure. Available memory falls as the context grows, until the system swaps, stalls, or kills a process. The symptom is that the same job slows down for no obvious reason late in a run.

    To tell which, measure again at the end of the long run with the same prompt and compare. If the two numbers differ, the difference is heat or memory. Then read the vitals log, which records available memory and GPU temperature every 30 seconds, so the slope is visible. A run that begins with 72 GiB available and ends with 18 has been under growing pressure, and the second number is the one a watchdog acts on.

    The project's watchdog ceiling for the GPU was 95 degrees Celsius, chosen to stop a run before the chip had to protect itself. If temperatures approach that over an hour, improve airflow or shorten runs. See Chapter 15 and Chapter 5.

    My unattended run just sits there and produces nothing. What is wrong?¶

    Most likely a permission rule is asking for an approval that nobody is there to give. Two kinds of tool, the file editing tool and the shell execution tool, do most of the work in a skill, and between them they let a model do nearly everything a person at a keyboard can. The permission model is the set of rules that decide whether a tool call is allowed: a rule can allow a call, forbid it, or require a person to approve it first. An interactive harness asks, and a person answers. An unattended harness has nobody to ask, so an approval rule stalls the run, and a paused run measures nothing.

    Decide every approval in advance, in one of two ways:

    • Allow the call in the harness configuration, inside a sandbox that limits what the agent can touch.
    • Put a standing answer in the prompt. The benchmark prompts carry a standing answer to the skill's approval questions, because no one is present during a run.

    Then confirm with a short test run that nothing pauses. The three-minute test in Chapter 17 is the right place to find out, not hour two of a long run.

    Related, and easy to confuse with a stall: if the model writes its tool call as ordinary text, the harness sees no tool call and the loop ends after one turn. That run ends rather than waits, and the log shows a reply with no tool call. See Chapter 16 and Chapter 22.

    Which files and commands print identifiers I might not expect?¶

    Several ordinary places record who a machine is:

    • /etc/dgx-release holds the unit's serial number. Read it with grep -v SERIAL /etc/dgx-release, and never paste its raw contents into a file you plan to publish.
    • /etc/machine-id holds a unique machine identifier.
    • ~/.ssh/known_hosts lists the hosts you have connected to.
    • Shell history records the commands you have run.
    • nvidia-smi can print a GPU's unique identifier, which ties a document to one machine.
    • Any log of a run shows /home/<user>/... on every line that touches a file, so one excerpt can reveal an account name dozens of times.

    A command that looks harmless can print an identifier on a line you did not expect. Treat every captured output as unsafe until you have read each line of it. Filter the known sources at capture time, for example with grep -v SERIAL, and then read it anyway.

    For paths, replace the home directory with a placeholder, and prefer paths relative to the project root, which carry no account at all.

    The strongest fix is upstream. A probe that never reads an identifier cannot leak it, which is why the probe suite leaves identifying fields out by default instead of cleaning them afterward. See Chapter 23 and Chapter 10.

    If the model runs locally, does that mean nothing leaves my machine?¶

    No. Running the model on your own machine keeps its prompts and tokens there, but anything else that reads the output can still send it away. A supervising cloud assistant that reviews the run, a scoring script that uploads results, or a log file shared for review can each carry generated text off the machine. "The model runs locally" is a statement about one component, not about the whole workflow.

    Even the model itself does not make a deployment closed. Weights and software are downloaded, and the request for them is visible to whoever hosts them. What changes is that your content, which is the sensitive part, no longer has to leave.

    The fix is to trace every place the generated text goes after the model writes it, and to put each destination in a table before you claim a boundary. This evaluation does exactly that with a data egress trace, and it records the supervising assistant as a destination, because the orchestrator is a cloud model and everything it reads back to monitor or score a run goes to its service. The generation loop kept its tokens local, and the supervision of it did not.

    Chapter 18 shows how to build the trace and how to check it. A packet capture would confirm what actually leaves, but it needs administrator rights, and this evaluation did not run one, so it states its boundary as a configuration and not as a verified result. See also Chapter 4.

    The calculator said "Fits", but my machine struggled or froze. Why?¶

    Because the estimate predicts the starting footprint, and a long run adds to it. The verdict is a floor, not a peak: the server's per-conversation state grows as a run proceeds, and the weights, the context, and the operating system all draw on one pool.

    The worked case in this evaluation is instructive. For gemma4:31b at a 262,144-token context, the calculator returns 73.7 GB against a 102.4 GB limit on a 128 GB unit, which is "Fits", and it matched the 71 GB measured with the model idle. That is also the configuration where a unit stopped responding a few minutes into a long run. The cause was not confirmed, and memory exhaustion is the leading suspect. A "Fits" at 73.7 GB means the idle state fits. It does not mean a long run is safe.

    If you got the arithmetic right and the machine still struggled, you have not made a mistake. Do three things:

    1. Treat the verdict as a gate on what to try, not as a guarantee.
    2. Choose the smallest context the job needs.
    3. Measure what actually happens with a vitals log, and put a memory watchdog on top, as Chapter 18 describes.

    On a discrete GPU, running out of memory stops one process. On unified memory it can freeze the machine, which is why the headroom is not a nicety. See Chapter 11.

    My DGX stopped responding during a long run. What happened, and what should I do?¶

    A system freeze is the machine ceasing to respond entirely: no SSH, no network, no output. On a unified-memory machine it is a recognizable consequence of exhausting the shared pool, because the same pool is what the operating system runs on. And since nothing remote can reach a machine that is not answering, the machine's administrator has to restart it.

    In this evaluation one unit stopped responding twice, each time a few minutes into a long run with the same model. The first was at a 256,000-token context. The second was at a smaller context, with a watchdog running, and the watchdog logged no action. So memory exhaustion as the only cause is not confirmed: heat, power, and the memory hardware itself were not ruled out.

    What to do:

    1. Before the next run, start the vitals log and a memory watchdog. A frozen machine takes its last readings with it, and the vitals log is what survives. The project's watchdog checks available memory and GPU temperature every five seconds. When memory falls below a floor, or the temperature passes a ceiling, it kills the harness containers and unloads every model. This evaluation ran it with a 20 GiB floor and a 95 degree Celsius ceiling.
    2. Reduce the context to the smallest value the job needs, because the KV cache reserves memory for the configured window.
    3. Read the last lines of the vitals log after the restart: available memory, GPU temperature, and power just before the stop.
    4. Do not claim a cause you have not confirmed. Write what you observed and what you ruled out.

    A watchdog is a safeguard against the failure you expect, not a diagnosis of the one you get. See Chapter 18, Chapter 11, and Chapter 10.

    How do I work out why a run failed?¶

    Work from the symptoms in the logs to the cause by asking what the evidence rules out, not what the failure feels like. Several different causes produce runs that look similar from the outside. The evidence is the run event stream, the final result, and the server log, and the questions are the same every time:

    • How many turns were taken?
    • How many tool calls (the tool call count), and how many failed?
    • What was the last thing the model said?
    • What was the peak context size, against the window?
    • Did the run end on its own, or was it stopped?

    Then match the symptom:

    Symptom Likely cause First thing to check
    One turn, last message looks like a call Text-emitted tool call The final message in the event stream
    An error, then a correct retry Malformed tool call The failed call's arguments
    Ends after announcing, no file written Premature turn termination The last message and the run directory
    Answers a greeting after several turns Task loss Peak context size against the window
    Forgets the task late in the run Context overflow Peak context size against the window
    Same error at turn one for every model Harness misconfiguration The base address, model name, and mounts

    A number alone does not diagnose. A 100% tool-call success rate on 28 calls is not better than 84% on 50 if the 28 never reached the step that writes the file. The count is the prompt for a question, and the event stream holds the answer. A run-report script prints turns, tool calls, failures, tokens, and time, and works on a run that is still going. See Chapter 22.

    Every model failed at the same step. Are the models the problem?¶

    Almost certainly not. A failure that appears for every model at the same place is a configuration or skill fault until shown otherwise. Harness misconfiguration is a fault in how the harness was set up and not in the model: a wrong address, a model name the server does not have, a skill folder that was not mounted, or a permission rule that stalls. Its signature is a failure at the very first turn, for every model, with an error message that names the configuration.

    Before you write that a model "cannot" do something, run the failing step with a model that is known to work. If it fails there too, you have found a configuration or skill fault, and the models were innocent.

    The same logic applies to defects in the skill itself. In this evaluation a faulty example in a skill produced navigation files that would not build, and a fast model that copied it was set aside. The skill was corrected, and the model was retested afterward. The point is that a symptom's cause has to be confirmed before an exclusion.

    Remember that stages are chained, so the failing stage is not always the faulty one. In three of one model's chapter runs, the skill's own chapter dependency check stopped the run because the model's chapter structure from stage 2 had placed concepts out of order. The failure was real and the stage that caused it was the earlier one, which is why chained stages must be diagnosed from the start. See Chapter 22 and Chapter 21.

    I committed something sensitive to the repository. What do I do?¶

    Stop, and tell the person responsible for the repository. Do not try to hide it with a quick follow-up commit. Git history persistence is the fact that a commit stays in a repository's history after a later commit removes its content. Deleting a leaked file in the next commit changes the latest version and leaves the leak in every earlier one, which anyone can read with git log -p. Every clone and fork made before the deletion keeps its own copy, and a deployed site is a separate copy again, with search engines holding their own.

    The order of operations follows from that:

    1. Stop and tell the repository's owner before doing anything else.
    2. Treat any leaked credential as compromised. Rotate it. Removing it from history does not un-expose it.
    3. Consider the site. A deployed documentation site is indexed in its own right, so its copy has to be dealt with too.
    4. Rewrite history only as a last resort. It is disruptive, it needs a force-push, and it still does not reach the copies made earlier.

    A public GitHub repository is readable by anyone, indexed by search engines, and scanned continuously by automated tools that look for credentials and addresses. Secrets committed to one are often found and tried within minutes.

    So prevention is the only real remedy, and the cheap time to catch a leak is before the commit. See Chapter 23 and Chapter 1.

    Best Practice Questions¶

    What should I record next to every benchmark result so it can be reproduced?¶

    Write the pin down on day one. Next to every result you keep, record:

    • the exact model tag,
    • the model file's checksum,
    • the inference server version, and
    • the date.

    A table of scores with no version beside each one cannot be reproduced and cannot be fairly compared. With a local deployment you can pin completely, because the weights file does not change unless you change it. With a cloud service you can request a specific version only while the provider offers it, and you cannot keep it past its deprecation, so a result recorded against a retired model can never be repeated.

    The same habit extends to the rest of the stack. Chapter 8 pins the Python version and exports the environment, Chapter 12 verifies file checksums on download, and Chapter 19 turns "same harness, same prompts" into lines in a record that say what the value was and how you know. Pinning is a precondition of a fair benchmark, because a result is only meaningful for the version that produced it. See Chapter 4.

    What habits keep a remote-access setup from becoming a liability?¶

    Chapter 7 calls them host hygiene, and five habits are enough:

    1. Keep private keys private. Never copy id_ed25519 to another machine, a chat, or a repository.
    2. Use one key per purpose. A separate key for the DGX project can be revoked without affecting anything else.
    3. Remove what you added. When the project ends, delete your public key from the server's authorized_keys and ask the administrator to remove the account.
    4. Tell the owner. Installing a key on a machine you do not own is a change to their security, and they are entitled to know.
    5. Read the output before saving it. A pasted SSH session contains hostnames and addresses, and Chapter 23 builds the review that catches them.

    The first and fifth bear directly on this book's public repository. Git history is permanent, so a private key committed once is exposed for good, and a pasted terminal session can carry a hostname or an address into a chapter without anyone noticing. See Chapter 7.

    Why take a read-only inventory first, and how do I do it?¶

    A five-minute read-only look tells you whether a plan is possible before you install anything: the architecture, the free space, whether Docker answers. Finding out after a two-hour download that the disk is full is a much worse way to learn it. It is also the right first step on a machine that belongs to someone else, because it needs no permission to install or change anything.

    A small set of standard Linux inventory commands covers the questions, and each prints a few lines and writes nothing:

    Question Command
    Which operating system? grep PRETTY_NAME /etc/os-release
    Which kernel and architecture? uname -srm
    Which processor? lscpu
    How much memory? free -h
    How much disk? df -h /
    Which GPU and driver? nvidia-smi
    Are containers available? docker --version
    Which groups am I in? id -nG

    To run a whole script without copying it to the machine, pipe it over SSH: ssh <user>@<dgx-host> 'bash -s' < inventory.sh > inventory.txt. The remote shell reads the script from standard input, so nothing is written to the DGX's disk.

    Read the output before you save or share it. An inventory describes a specific machine, and some files, such as the DGX release file, contain a serial number. See Chapter 9.

    How do I stop a model from padding a section to reach its word target?¶

    Treat the target as a guideline, not a quota. A model that sees "500 words" will often manufacture 500 words by restating itself. The remedy is to read a short section against its target and ask what is missing. If the answer is "nothing", the section is finished, and adding words only lowers quality.

    The book's anti-padding rules state this as four instructions:

    1. Quality over quantity. A dense, correct section beats a padded one that reaches the number.
    2. Expand by showing, not telling. If a section is thin, add a worked example, another simulation, or more technical detail, and never restate earlier paragraphs.
    3. No formulaic templates. Avoid boilerplate such as "Let's talk about X" and weave concepts into flowing narrative.
    4. Examples over prose. Prefer a short commented example or a MicroSim to a long description of abstract logic.

    Put these rules in a file the agent can re-read, as this book does in its content generation guide. A rule that lives only in a prompt is lost when the context fills up, while a rule in a file can be read again, and the same file makes two runs comparable. See Chapter 2.

    How should I read a model card?¶

    Read it like a marketing page with facts in it. A model card is the document a publisher releases with a model, describing its purpose, training, benchmark results, limits, and license. It is the fastest way to learn the size, the context window, and the license, so read those fields first and trust them.

    Treat everything else as the publisher's own claim, to be tested. Benchmark scores and statements of strength describe what the publisher optimized for. They do not describe the conditions under which the property fails, and your workload may be one of them. Never carry a card's score into your report as a measured result.

    Apply three license questions to every model. Is commercial use allowed? Are there size or revenue exceptions? And is the license actually stated by the publisher, or only reported by a third party? This evaluation records a license that was reported without independent verification as "reported", not as confirmed. See Chapter 3 and Chapter 12.

    Which assumptions in a cost model deserve the most attention?¶

    Find out by running a sensitivity analysis: change one assumption at a time, record how the output moves, restore it, and then change the next. Varying two together means you cannot say which one moved the answer. The cost analysis ran it on the reference case:

    Change Cost per book Price at 20% margin
    Reference case $53 $66
    Operations labor of 8 hours a month $81 $101
    No operations labor $25 $32
    Hardware at $9,000 $57 $72
    Hardware at the launch price of $3,999 $47 $58
    The three stages are 5% of the book $106 $132

    The result is a ranking of what to worry about. Labor, and the share of the whole book that the benchmark's three stages represent, move the answer by as much as a factor of two. The hardware price moves it by about ten percent. A planner who spent a week negotiating the hardware price and an hour on the labor estimate had the effort the wrong way round.

    Treat the cost model's output as a model, not a measurement, and respond to a surprising number by inspecting an assumption. See Chapter 6.

    How do I prove that my environment specification actually rebuilds?¶

    A specification you have never rebuilt from is an unverified claim, and the rebuild is the test. Create a throwaway environment from the file, check that it works, compare its package list with the original's, and delete it:

    conda env create -n dgx-test -f environment.yml
conda run -n dgx-test tailscale version
diff <(conda list -n dgx --export) <(conda list -n dgx-test --export)
conda env remove -n dgx-test

    An empty diff means the rebuild matches. A few differing lines are the packages that were not pinned and resolved to a newer release, and they are exactly what to pin next.

    Watch how you export. A full conda env export records exact builds that are specific to one platform. Taken on a Mac with an Arm laptop chip, it lists builds that do not exist for a Linux aarch64 DGX, and the rebuild fails with a list of packages that cannot be found. conda env export --from-history records only the packages you asked for and crosses platforms, at the price of letting each dependency resolve to whatever is current unless you pin it yourself.

    Remember what a specification does not cover: the operating system, the GPU driver, system CUDA libraries, and model weights. See Chapter 8.

    What rules should every probe script follow?¶

    A good probe script follows four rules, and each one prevents a specific failure:

    Rule Failure it prevents
    Read only, never write A probe that changes the machine it is measuring
    Standard library only A probe that cannot run on a fresh machine without an install
    Bounded run time A probe that hangs forever when a tool misbehaves
    Report unknown as null, never guess A report that looks complete and hides a failed measurement

    The last rule is the one people skip. A probe that returns zero when it cannot read a value turns a failed measurement into a machine with no memory. Return null for anything you could not read, and a reader can tell a missing measurement from a measured zero. Not Supported and [N/A] from nvidia-smi should become None, not 0.

    The base of every probe is a helper that runs a command and returns its text, or None if the command is missing, fails, or takes longer than a timeout. A missing nvidia-smi on a machine without a GPU then produces an empty answer instead of a crash.

    Standard library only is a deliberate cost. Without psutil, you read memory from /proc/meminfo and parse nvidia-smi text, but the probe runs on a machine that has nothing installed. See Chapter 10.

    What should I log during a long run, and how often?¶

    Start vitals logging before any long run. Record a few measurements at a fixed interval, 30 seconds works well, so that a machine that fails leaves its last readings behind. Three are enough: available memory, GPU temperature, and GPU power draw.

    import json, os, time

with open("vitals.txt", "a") as out:
    while True:
        gpu = probe_gpu()["gpus"]
        row = {"t": int(time.time()),
               "mem_available_gib": probe_ram()["available_gib"],
               "gpu_temp_c": gpu[0]["temperature_c"] if gpu else None,
               "gpu_power_w": gpu[0]["power_w"] if gpu else None}
        out.write(json.dumps(row) + "\n")
        out.flush()
        os.fsync(out.fileno())
        time.sleep(30)

    The flush and fsync calls matter. They ask the operating system to put each line on the disk now, because a machine that freezes does not get to finish its buffers.

    A machine that overheats or freezes cannot tell you what happened afterward, so the last line the log wrote becomes your evidence. This is the idea behind the project's log_vitals.sh script, which was added after a unit stopped responding and left no record of why. Pair the log with a watchdog that acts on the same readings, as Chapter 18 describes. See also Chapter 10.

    How do I decide which models are worth testing?¶

    Start from the workload, not from a leaderboard. For this course's workload, which is running a long skill through an agent harness, four criteria cover it, and each can be checked before downloading:

    Criterion Why the workload needs it
    Supports tool calling A harness acts only through tool calls
    Context window of at least 64,000 tokens The harness prompt alone takes about 19,000 tokens
    Fits with headroom A model that fits tightly can freeze a unified-memory machine
    Identifiable publisher and checkable terms A result cannot be recommended if readers cannot check the license

    Read each candidate's model repository on the Hugging Face Hub, the main public site for sharing models, as the primary source: who published it, the license file, the model card, the file list, and the history.

    Use leaderboards and public benchmark scores to build a long list, not to decide. They answer a question that is rarely yours, since a general-knowledge or coding score says little about whether a model follows a thousand-line skill or keeps a blank line before every list.

    Read publisher claims as hypotheses. This evaluation's candidate page states each claim and then what testing found, for example a model "built for long agent tasks" that produced the cleanest learning graph and was by far the slowest. Neither tool-calling reliability nor writing quality can be read from a model's name; both are measured, in Chapter 19 and Chapter 20. See Chapter 12.

    Who should reach my inference endpoint, and how do I share it?¶

    Start closed and open deliberately. An Ollama endpoint has no login of its own, so anyone who can send it a request can use the machine's GPU and tie up its memory. localhost binding keeps it private: the server listens only on 127.0.0.1, and a request from any other machine, even one on the same network, is refused before it reaches the server.

    Confirm everything works there, and then choose how to share it with exactly the people who need it:

    Method Who can reach the endpoint Changes on the DGX
    SSH port forward Only you, for as long as the forward runs None
    Tailscale Serve Tailnet members the access rules allow Needs the client and a command on the DGX
    Bind to all interfaces (0.0.0.0) Anyone who can reach the port A server setting

    This evaluation used the SSH forward, because it costs nothing on the DGX and exposes nothing. Tailscale Serve publishes the loopback port to the tailnet over HTTPS while the server stays bound to loopback, and the access control list still applies. Check tailscale serve --help, because flags have changed across versions.

    Binding to every interface to make a tutorial command work is a decision you cannot easily see later. After you open anything, test from a second machine that the endpoint is refused where you expect it to be. See Chapter 13.

    Which setting should I change first to speed up a run?¶

    The one aimed at your bottleneck, and only one at a time. Performance optimization is changing a single setting and measuring the result against a fixed baseline. A comparison between two runs that differ in three settings tells you nothing about which one mattered.

    First find where the time goes with a time breakdown: loading, reading, writing, and tool time. Then match the setting to the cause:

    Setting What it moves What it costs
    Quantization to fewer bits Generation speed up, memory down Some quality
    Context length down Memory down, room for the system up Smaller conversations
    Keep-alive up Fewer reloads Memory held while idle
    Prompt caching working Prompt processing time down per turn Nothing, when it works
    Batching and concurrency up Throughput up Latency per request
    Sampling parameters The output, not the speed Different results

    The last row is the trap. Temperature, top-p, and top-k change the output and have little effect on speed, so a reader looking for speed will not find it there, and a benchmark must fix and record them or its runs are not comparable. Quantization is the one dial that changes both speed and quality, so whether the loss matters is a measurement.

    Batching helps a service that handles many sessions at once. For one benchmark session at a time, it is a lever left unused. See Chapter 15.

    How do I confirm a model works in the harness before a long run?¶

    Run the three-minute test before the three-hour one. A model that fails the short skill will fail the long one more slowly. The check this project uses is a short run of the course-description analyzer skill, whose output can be inspected quickly. Skill execution verification passes when four things are true:

    • The report was written. The skill's output file exists.
    • A score was given. The report contains the quality score the skill is meant to assign.
    • The project files were updated. The frontmatter and the site navigation reflect the skill's work.
    • The site builds. A strict mkdocs build finishes with no errors.

    A script applies exactly these four checks, so the verdict does not depend on someone reading the output. Put the analyzer run, with its scripted checks, in front of every model you intend to benchmark, and discard the ones that fail for reasons you can name.

    A harness compatibility test runs the same short skill against several harness and model combinations, to find which pairs work at all. Failures at this stage are cheap and informative. In this evaluation it showed a model that wrote its first tool call as plain text and a model that lost the task after a few turns, both within minutes, and neither would have been found by a first-prompt smoke test, which tests only the server. See Chapter 17.

    How do I write a good evaluation question and choose metrics?¶

    A good question names what is being compared, on what task, under what conditions, and what would count as an answer. The test is whether you can imagine two different outcomes. If you cannot, it is not a question for an experiment.

    Poor question Why it fails Better question
    Which model is best? Best at what, for whom? Which candidate completes stages 1 to 3 on Algebra I with the fewest structural faults on one DGX unit?
    Is local cheaper than cloud? Mixes cost and price, and ignores quality What is the cost per textbook at the measured speed, and what would a service charge at a 20% margin?
    Does the DGX work? Nothing could ever answer "no" Does a local model produce a learning graph that passes structural checks within a 150-minute limit?

    Then do metric selection, and do it before you see the data. A useful metric answers the question, can be computed the same way for every run, and was decided in advance. The evaluation groups them as completion (stage finished, files present, build succeeds), efficiency (wall-clock time, tool calls, failed tool calls, tokens, peak memory), and quality (structural checks, reading level, human review). Completion and efficiency are computed by a program and are repeatable. Quality matters most and is hardest to measure.

    If you look at the data and then choose the measure that favors your favorite model, you have not run an experiment. Write the metrics and how each is computed into the record first, and add new ones afterward only as clearly labeled extras. See Chapter 19.

    What should I record about each run so the result can be checked later?¶

    Logging is recording what happened during a run in enough detail to reconstruct it, because the log is the difference between a measurement and a memory, and a surprising result can only be investigated later if the record exists. This evaluation keeps six records for each run:

    Record What it holds Answers
    The event stream Every message, tool call, and result What did the agent actually do?
    The final result Turns, token counts, timings How much did it use?
    The status file Exit code and wall-clock seconds Did it finish, and how long?
    The server log Loads, memory, request timings Why was it slow?
    The vitals log Memory, temperature, power every 30 seconds What did the machine look like?
    The configuration Versions, settings, dates Can this be repeated?

    Then state your explicit assumptions and label every number as measured or assumed, the distinction the book calls measured versus assumed values. A measured value came from an observation in this evaluation, and an assumed one came from a rule, a published figure, or a guess. The cost analysis does this: six of its ten speeds are assumed, and it tests its own rule against the one case it can check. The rule predicted 34 tokens a second for one model, and the measured figure was 26. Reporting the miss is what makes the other assumptions credible.

    Finally, keep a design decision record: what was chosen, what else was considered, and why, along with who decided. Attribution matters because a choice made by a person with a goal and a choice made by an assistant filling a gap deserve different scrutiny. See Chapter 19 and the Design Choices appendix.

    Why test a model on its own before testing it in the harness?¶

    Because failures are cheap and diagnosable when the layers are separated. Two-layer testing runs a model-only test first, sending short, fixed tasks directly through the server with no harness, and then a harness smoke test.

    Layer Time per model What a failure means
    Model-only test Minutes The model cannot follow a rule on its own, such as a blank line before a list
    Harness smoke test About three minutes The model cannot work through a skill with tools
    Full stage Tens of minutes to hours The model fails at scale, or is too slow

    A model that fails the first layer fails in seconds and for a reason you can name. A model that passes it and fails the second fails for a reason that involves the harness. Going straight to the full pipeline makes every failure slow and mixes the causes. The project's model-only test has five tasks: Markdown writing, p5.js code, schema-constrained JSON, a tool call, and a 30,000-token prompt.

    The 30,000-token task is a long-context recall test: a value is placed in a long block of text and the model is asked to return it. It found something the other tasks did not. One model returned the wrong value in two of its model-only runs and again in a third.

    When a result traces to a faulty check or a faulty skill example, that is the evaluation working. Correct the defect, retest the models it touched, and note which conclusions changed. See Chapter 19.

    How do I calibrate a check before trusting it?¶

    Test the checks themselves, on inputs whose answers you know, before you trust them on real output. Scoring check calibration matters because a check can be wrong in two directions: it can pass a bad result, or it can fail a good one. The second is easy to miss because it looks like a model failure.

    This evaluation met it. The first versions of three model-only checks were too strict and failed output that was correct. Each was fixed and the saved output was scored again. Without that step, a model would have been marked down for a defect in the test.

    A calibration set for a check is small:

    1. A known-good input that must pass.
    2. A known-bad input that must fail, for the reason it should.
    3. An edge case at the threshold. For a 32-character label limit, test a label of exactly 32 characters and one of 33.

    Run the set whenever you change a check, and save raw output so you can rescore it without rerunning the model. The same idea at the level of the whole experiment is the retest after a fix: when a result traces to a faulty check, correct the defect, rescore or rerun what it touched, and note which conclusions changed. See Chapter 20 and Chapter 19.

    How should I report provisional, negative, and limited results?¶

    Label them as what they are, with the same care as a success.

    Provisional results are real observations that are not yet established, because they rest on too few runs, an unvalidated check, or an incomplete review. Every result from a first round is provisional. Use them to decide what to test next, not to write a recommendation.

    Negative results are findings. A model that lost the task after a few steps, one that wrote its first tool call as plain text so the run ended after one turn, and one that could not fit a usable context all tell a reader choosing a model for their own machine more than the successes do. Report the failure, the evidence, and your best account of the cause, with your confidence stated, since several causes in this evaluation were never identified.

    A limitations statement says what the result does not show. This evaluation's carries concrete items: each model was run once, so rankings are not supported; one course, one machine type, one harness, and one skills version; structural checks only, with no completed human review; no cloud baseline; six of ten speeds in the cost analysis assumed; and reasoning mode not held constant.

    Then write a design critique before someone else does, pairing each flaw with its effect and its repair, such as "one run per model" with "rankings could be noise" and "three to five runs each". See Chapter 20.

    Why does the benchmark runner copy the starting directory for every run?¶

    So that a run can never change its own input. The template is never the working copy: a run works on a copy, and the original stays byte for byte what it was. That is the whole mechanism by which a failed run, a killed run, or a run that wrote garbage cannot reach the next one. If a run changes its own starting point, you can never again say what it started from.

    The benchmark runner does five things in order:

    1. Copies the starting directory to a fresh run directory.
    2. Starts the harness container with that directory mounted and the model's tag set.
    3. Feeds the prompt file in and captures every event.
    4. Stops the run at its time limit if the limit is reached.
    5. Records the exit code and the wall-clock seconds.

    For stage 1 the starting directory is the benchmark workspace template, which holds the unchanged course description and the site configuration. For each later stage it is the previous stage's run directory, which is how work accumulates through stage chaining.

    The time limits are 150 minutes for stage 1, 2 hours for stage 2, and 90 minutes for each chapter in stage 3. A run stopped by its limit exits with code 124 and keeps what it wrote, so a timeout is a result and not a lost run. See Chapter 21.

    When is it fair to leave a model off the shortlist?¶

    When you can state the criterion that excluded it, and you have confirmed the cause. A model shortlist is the written list of candidates you will test, each with its reasons, and the exclusion rationale is the reason a model was left off. The second matters as much as the first, because a reader who sees a famous model missing will wonder whether you missed it. One line each, tied to a criterion, answers them. For example, this evaluation left out a 122-billion-parameter model because at 81 GB it was a very large download and gpt-oss:120b already covered the large tier.

    The harder case is excluding a model for a fault. This evaluation set aside its fastest model partly for broken navigation files, and the fault turned out to be a faulty example in the skill that the model had copied. The model was set aside before it was retested against the corrected skill. It was retested afterward and passed the short skill test, which is the order to avoid. An exclusion based on a symptom needs the cause confirmed, and an exclusion that has not been retested should say so in its rationale.

    So before you write that a model "cannot" do something, check whether the failure is in the model or in the setup around it: the skill, the harness configuration, or the prompt. Chapter 22 returns to this with a quick test, and Chapter 14 reminds you that one run is an observation, not a ranking. See Chapter 12.

    How many times should I repeat a run before trusting a result?¶

    More than once, and the number depends on what you want to claim. A language model samples its output, and a long agent session takes a path that depends on small differences early on, so two runs of the same configuration are not the same run. Run variance is how much the results differ among repeated runs, and sample size is the number of runs behind a conclusion.

    Runs per configuration What you can say
    1 What happened; which things failed outright
    3 Whether the result is stable, roughly
    5 or more A typical value and a range, with caution

    Here is why. Suppose a model finishes a stage in 20 minutes on one run and 45 on another, because in the second it made a wrong turn and recovered. A second model finishes in 30 minutes on its one run. Ranking the second ahead of the first from those numbers is a coin flip. With five runs of each, the spread is visible and the comparison can be stated with its uncertainty.

    Nearly every result in this evaluation so far is one run, which is enough to find what fails and not enough to rank. Say so when you report it.

    Add a control run: repeat a run that should give the same answer, to check the apparatus and not the subject. If the control differs from the original by more than the expected variation, something changed between them, such as memory pressure, a thermal state, or a server setting. A control is the first thing to do when a surprising number appears. See Chapter 19.

    How can I tell whether a cloud baseline is a fair comparison?¶

    Ask three questions of any baseline:

    1. Did it use the same inputs?
    2. Is its configuration recorded?
    3. Was it scored by the same method as the thing you are comparing it to?

    A baseline that fails any of the three is a reference point, and the comparison should call it that. A baseline comparison judges a result against a reference produced under the same rules, and a fair comparison is one in which the only meaningful difference between the two sides is the thing being compared.

    This evaluation applies the test to itself, honestly. It has a reference for scale and not yet a baseline. The published Algebra I book was made with cloud models and has 200 concepts and 13 chapters of about 55,000 words, but:

    Requirement for a fair comparison Satisfied by the published book?
    Same course description Yes
    Same skill versions No, earlier versions
    Same prompts Not recorded
    Timings and token counts recorded No
    Same scoring applied Not yet

    The book shows how large a finished book is. It cannot say how long a cloud model takes or how good its output is under these exact conditions. The cloud baseline remains to be run, and until it is, the comparison should say "reference for scale". See Chapter 19 and Chapter 4.

    Should I use a language model to judge the generated chapters?¶

    Only as an instrument you have calibrated, and with its costs in view. LLM-as-judge is fast, cheap, and scales to thousands of outputs, and it is also the largest source of bias in this kind of evaluation. Bias in evaluation is a systematic tilt toward some results for reasons unrelated to quality. Unlike noise, it does not average out over many runs: it points the same way every time.

    Weakness What it does to a score Mitigation
    Self-preference Rates output like its own higher Use a different model family as judge
    Verbosity Rewards length Control for length, or score against a rubric
    Position Prefers the first candidate Randomize order and score twice
    Confidence Rewards fluent errors Require evidence for each rubric score
    Data exposure Sends generated text to a service Use a local judge, or do not use one

    The last row has nothing to do with accuracy. Sending a local model's output to a cloud model to be scored sends the text to the cloud, which undoes the reason for generating it locally. This evaluation recorded that as the reason it did not use an LLM judge as its scoring method.

    Treat a judge as another model under test. Calibrate it against human scores on a sample before you trust it on the rest. If its scores disagree with the people's on the cases you checked, it has told you something about itself, not about the outputs.

    The right test of quality is blind human review: a person scores output against the rubric without knowing which model produced it, in randomized order. It is slow and costs money, so use two reviewers on a sample and record their disagreement, which measures how much the rubric leaves to taste. See Chapter 20.

    How do I run a queue of ten models so it survives disconnects and freezes?¶

    A benchmark of ten models is a queue, and a queue needs more than the runner. This project's batch script works through the models one at a time, in phases: download and model-only test, harness smoke test, then stages 1, 2, and 3. Three practices make it survivable:

    • Run it in tmux. The queue runs in a session named bench, with the watchdog in a session named watchdog, so a dropped connection stops neither.
    • Choose each model's context on purpose. The script restarts the server for each model with a context chosen from a memory estimate that keeps about 45 GiB free, not one value for all models.
    • Fetch as you go. Each model's results come back as it finishes, so a unit that freezes does not take unfetched results with it.

    Two small mechanisms help. A run that already has a status file is skipped, so a stopped queue restarts where it left off. And an empty file named skip-<model> in the runs directory makes a running queue pass over that model.

    Also stop early when it is pointless. A stage 3 queue stops after two time-outs in a row, because a model that cannot finish two chapters in 90 minutes each will not finish twelve, and the remaining runs would only occupy the machine. The runs not made are recorded as "not run", with the reason, in a status table with a "last updated" line. See Chapter 21 and Evaluation Status.

    What safeguards keep device details out of the repository?¶

    Use several layers, because each catches a different kind of slip:

    Layer What it does What it misses
    Raw output isolation Keeps unsanitized output outside the repository, so nothing has to be removed because it never entered it A file someone copies in by hand
    Gitignore rules Refuse patterns such as *.log, *.jsonl, .env, id_*, *.pem Files already tracked, and an explicit git add -f
    Hosts via environment variable Real addresses live in the shell of the person running the script, never in a file A value typed into a document
    A narrow publishing script Copies only a model's learning graph, chapter text, and the course description, and leaves out any file with an address, a host name, or a home-directory path Nothing it does not copy, which is the point: it fails closed
    Secret scanning (gitleaks) Finds strings with the shape of a credential, in the tree, staged changes, or history An IP address in a paragraph or a hostname in a caption
    Pre-commit scan Refuses a commit whose added lines match address, tailnet, key, token, home-path, or serial patterns Anything that does not match a pattern
    Publication safety review A person reads everything against the catalog Nothing a person reads carefully, but it is slow

    Make the scan part of the publish command. A check you must remember to run will be skipped on the tired evening that matters most, so put it in the same script as git commit and the site deploy.

    A pre-commit hit is a prompt to read the line, not proof of a leak: a version number can match the address pattern. Check your own diff before every commit as well. See Chapter 23.

    Advanced Topics Questions¶

    How do I find break-even volume, and why check capacity?¶

    The break-even volume is the amount of production at which two options cost the same. For a local machine against a per-book price, it is the fixed cost divided by the saving on each book:

    N* = F ÷ (P − v)

    Here F is the local fixed cost for the year, P is the alternative's price per book, and v is the local variable cost per book. With F = $8,275 and v = $0.58, and using illustrative prices rather than quotes from any provider:

    Alternative price per book Break-even books per year Reachable by one unit at 156 books a year?
    $100 83 Yes
    $50 167 No
    $20 426 No

    The last column is the part most often missed. A break-even above what the machine can produce is not a target to grow into. It means that against that alternative, one unit does not break even at any volume it can reach. Compute the machine's capacity as generating hours divided by hours per book, and compare. The formula also has no answer when P is less than or equal to v, because the alternative is then cheaper at every volume.

    See Chapter 6, and the Local Versus Cloud Break-Even Explorer MicroSim there.

    What did the first round show that no name, size, or leaderboard predicted?¶

    Four results contradicted the obvious expectation, and none could have been read from a model's name, size, or published score:

    • The model built for long agent tasks was the cleanest and the slowest. qwen3.8:27b produced a learning graph with exactly 200 concepts, no cycles, and no duplicate labels, and it took 102 minutes where the five others that finished took 6 to 22. In the chapter-writing stage it could not finish a chapter inside 90 minutes.
    • The fastest model wrote a flawed graph. gemma4:26b ran at 86 to 130 tokens per second and finished in under six minutes, with 40 duplicate concept labels out of 200.
    • The largest dense model did not fit with a usable context. mistral-medium-3.5:128b ran at 3 tokens per second and used 88 GiB at a 32,000-token context, so no context of 64,000 tokens or more would fit.
    • A model built to drive software-engineering agents did no work in the harness. devstral-small-2:24b wrote its first tool call as plain text both times, so the harness saw no tool call and the run ended after one turn. A second model, gpt-oss:120b, printed a tool call as plain text in one of its runs.

    The caution that goes with the table matters as much as the table. Every figure is a single attempt, and a model that failed once may succeed on a second try, as one candidate did after its skill was corrected. Treat the first round as a way to decide what to test further, and repeat a run before you write a sentence that begins "model X cannot". See Chapter 14.

    What are the weaknesses in this evaluation's own design?¶

    The book states them, which is what makes the results credible. An uncontrolled variable is something that could affect the result and that the design did not hold fixed. The honest response is to record it and say which direction it might push. This evaluation had at least three:

    • Reasoning mode. The model-only tests ran with reasoning turned off to bound their time, while the harness runs used each model's own default. One model spent nineteen minutes on a single turn, and predictions from the model-only test did not match.
    • Context length. It was chosen for each model from a memory estimate, so the models did not all run at the same setting.
    • Server behavior. One model's server re-read the conversation on every turn and the cause was not identified, so a speed difference could belong to the server and not to the model.

    There are structural limits too:

    • Single runs. Nearly every result is one attempt per model per stage, enough to find what fails and not enough to rank.
    • No cloud baseline yet. The published Algebra I book is a reference for scale, not a baseline under the same rules.
    • Assumed speeds. Six of the ten speeds in the cost analysis are assumed to equal a measured model.
    • One hardware configuration. All ten candidates ran on DGX units of the same type, so the timings and fit verdicts do not transfer to a different DGX without re-running the probes.

    An experimental design critique applies these standards to your own evaluation, in writing, before someone else does. Work down the same list: the question, what varies, what is held fixed, what is recorded, how many runs, and what the comparison is against. See Chapter 19 and Chapter 20.

    What is quality-adjusted cost, and why include human review?¶

    Quality-adjusted cost corrects the generation cost for the quality of what came out: how much of it is usable, and what it costs a person to review it. A book generated for $53 of which only 10 of 13 chapters are written has not cost $53 for a book. One way to express the first part is the cost per usable chapter: the cost divided by the chapters that met the completion criterion.

    Case Cost to generate Usable chapters Cost per usable chapter
    All 13 chapters complete $52.92 13 $4.07
    10 of 13 complete $52.92 10 $5.29
    6 of 13 complete $52.92 6 $8.82

    A model that writes only 6 of 13 chapters therefore costs $8.82 per usable chapter, more than twice the $4.07 of a complete book, however fast it is.

    Human review cost is the price of the person who judges quality. It is not in the generation cost, and it can be much larger. Ten hours of subject-expert review at $90 an hour is $900, seventeen times the $53 generation cost. A quality-adjusted comparison that leaves it out has priced the book as though nobody had to read it.

    The service price calculation is a separate step: the price a service would have to charge to keep a margin is the cost divided by one minus the margin, so $52.92 at a 20% margin becomes $66.15. That price covers generation only, and review is a separate and larger cost, so a comparison that stops at the generation price leaves out the biggest line. See Chapter 22.

    How do I decide whether a DGX is sufficient for textbook generation?¶

    Write the thresholds down before you see the data. A machine is sufficient for a purpose, and the purpose has to say how fast, how good, and at what cost. If you decide what counts as enough after seeing what the machine can do, the answer is always yes.

    A DGX sufficiency judgment is a judgment, not a calculation, and the criteria this evaluation can state are concrete:

    1. Does at least one model complete all three stages without a fault that makes the output unusable?
    2. Does it do so within a time and cost the user can accept?
    3. Does the quality, once reviewed, meet the standard the course sets?

    The honest answer at any given moment can be that the first is established, the second is estimated, and the third is not yet known, and a report says which. On the evidence the book has, this evaluation has no cloud baseline textbook yet and no completed human review, so it can state costs and structural results and cannot state a quality gap.

    When you do your own, use the probes' report for the hardware facts, the fit calculation for memory, the run reports for time, and the cost model for cost. Keep what you measured separate from what you assumed, and carry the same caveats into the recommendation. See Chapter 22 and Evaluation Status.

    How do I write a local, cloud, or hybrid recommendation I can defend?¶

    Structure the report in five parts, in this order, so that a reader can judge the conclusion for themselves:

    Part What it states The question a reader asks of it
    Question What was being evaluated, for whom Is this my question?
    Method The design: variables, inputs, runs, metrics Could I repeat it, and was it fair?
    Results What was measured, with the assumed marked What actually happened?
    Limitations What the results do not show How far can I trust this?
    Recommendation Local, cloud, or hybrid, and the conditions What should I do?

    Then state the recommendation as rules, because a reader can apply rules to their own circumstances and cannot apply a verdict:

    If the evidence shows Then the recommendation leans
    A local model completes every stage, at a cost per book below the service price, and review finds the quality acceptable Local
    No local model completes a stage the skills need Cloud for that stage
    Local completes the high-volume or sensitive stages and fails a hard one Hybrid, routed by stage
    Quality is acceptable and the cost depends on utilization the user cannot reach Cloud, or a shared unit

    An illustrative reading from this evaluation's provisional first round: several models completed the learning-graph and chapter-structure stages, and chapter text exposed the capability differences. That pattern would point to a hybrid with the structural stages local and a stronger model for the hard prose, until a local model's prose is reviewed. If the evidence is mixed, say so and state what would change your mind. See Chapter 22.

    What would a complete capstone evaluation of my own DGX involve?¶

    The capstone evaluation is a complete, objective evaluation of a DGX system, published. It uses every chapter, and sanitization is a graded step and not an afterthought. The steps follow the order of the book:

    1. Reach the machine. Join the tailnet, prove the connection at three layers, and log in without a password (Chapter 7 and Chapter 9).
    2. Probe the hardware. Run the probe suite and produce a report with identifying fields left out by default (Chapter 5 and Chapter 10).
    3. Choose and install a model. Compute the fit, select and download a model, and put it behind a local endpoint that only you can reach (Chapter 11 to Chapter 13).
    4. Connect and contain the harness. Install the skills, point a harness at the endpoint, run it in a container, and start the watchdog and the vitals log (Chapter 16 to Chapter 18).
    5. Design the experiment. State the question, the variable, the controls, and the metrics before running anything (Chapter 19).
    6. Run and score. Run each stage from a fixed template, apply the checks, and calibrate them (Chapter 20 and Chapter 21).
    7. Diagnose, cost, and decide. Explain each failure, compute cost per textbook, compare with a baseline, and write the report (Chapter 22).
    8. Sanitize and publish. Redact, scan, review, and publish only what passes (Chapter 23).

    The capstone is finished when the report is public and the review has found nothing in it that makes the machine easier to find, reach, or log in to.
